## What is now implemented

### 1. The Manager's wake for a child's question survives a restart
- `delegations` gained `wake_state` (`pending` / `sent` / `dropped`), `wake_title` (the request's short title only, max 160) and `wake_kind`, and an index on pending wakes. The claim is one conditional UPDATE that stores them in the same statement (`status='running'`, and refused while an older wake is still `pending`, never overwritten). Settling is keyed on `(assignment, request)` and only from `pending`, so a late ack for an older request cannot mark a newer one sent.
- Acknowledged only after a real delivery: directly, or by the team queue drain (`settle_queued_wake`). Dropped when the assignment ends (`finish`), when the question is answered, dismissed, expired or closed (`question_resolved`), or when its queued item is skipped for a finished assignment.
- Boot re-offer (`offer_wake`): only if the assignment is still running, the Manager conversation still exists and is not archived, and the card is still pending; otherwise `dropped` and nothing is sent (cancelled or deleted parent is safe). The ambiguous case (died between accepting the prompt and the ack) is decided from the Manager's stored messages: a user message with the exact wake text means `sent`; a lookup error means `dropped`; absence means the wake is queued once through the same path replies use.
- Privacy: the stored data is the bot name's text, a 160-character title and the kind. No question, option or answer text is stored, logged or sent.

### 2. Cancel is checked against the turn it means to stop
`cancel_session_turn_if(session, expected_turn)` compares the live turn **inside the per-session gate** (the same gate every turn reservation needs). On a mismatch it cancels nothing, writes no state and drops no retry, and answers `{cancellationRequested:false, reason:"turn_changed"}`. `delegation.cancel` uses it; `session.cancel` is the unchanged no-expectation form. On `turn_changed`, `cancel_row` re-reads once: its own turn ended -> the row takes the turn's own outcome; another turn is live -> only the row ends as cancelled and the session is untouched. The pending retry is dropped only after the check passed.

### 3. A failure after the prompt may have been written is explicit, never auto-replayed
Reading `session_prompt_impl` showed that no synchronous return happens after the adapter was invoked: it reserves the turn and spawns `run_turn`, which makes the one adapter call. So the ambiguity lives on the turn (`delivery: "unknown"` when the turn ends without `PromptAccepted`). Implemented:
- Error code `delivery_unknown` (409), one fixed sentence, returned by the `clientMessageId` **replay** when the earlier attempt's turn ended without confirmed delivery. `confirmResend:true` sends it again as a new turn (the newest row with that id wins the next replay).
- Automatic retry declines a retryable failure on a turn whose delivery is unknown (`DeclineReason::DeliveryUnknown`, content-free note). Watchdog continuations and retries only ever send new fixed prompts, never the original text.
- The queue path marks a `delivery_unknown` send failed + `ambiguous` and never requeues it (boot rewrite and the `confirmResend` gate from round 1 are unchanged).
- UI: a pending message that gets `delivery_unknown` shows "Bitbots could not confirm the bot received this ... check the conversation" with **Send again** (explicit `confirmResend`); a failed turn with unconfirmed delivery says so and that it will not be sent again on its own.

### 4. Exhausted limited sessions
`watchdog_due_sessions` no longer returns sessions that can never be enqueued (`recovery_count>=3`, automation), so the 1-second sweep stops re-querying them. A session whose automatic continuations are used up is settled once (one conditional UPDATE) to `idle`, with `autoContinueExhausted`, `limited_until` and `continuation_pending` cleared, one content-free notice (**"Automatic continuation stopped after 3 tries. Send a message to continue."**) and a `session.changed`. The same settle runs from the usage-limit branch, `continue_on_activation` and `sweep`; a user prompt still wins and resets the counters (and the flag). Caps, unattended rules and manual resume are unchanged.

### 5. Optional: pause new hand-offs
`delegation.paused` (boolean, default false; in the backup allowlist; not writable remotely). While true, a **Manager-initiated** new assignment (`message_blob`) is refused with a sentence the Manager can relay; replays of an already-recorded assignment, running or queued work, approvals, questions, replies, wakes and Stop are never touched. Decision of the Director: an assignment the owner **approved** (`assign_task`) is exempt (`delegate_approved`), because a pause must not make an approval fail. Settings › Manager has the switch (`ui/DelegationPause.tsx`).

### 6. Copy that cannot overpromise
`session.model.plan` text for providers that keep the session now says what is asked, not what will happen ("Your next message asks Codex to continue this thread on the new model. If Codex cannot, that message fails with its reason and the model is not changed silently."); same for Claude Code and OpenCode. There is no success claim before the provider answers.

## Not done: bounded `app.snapshot`
Investigated, deliberately not changed. The desktop already hydrates conversations lazily with `session.get` (`hydrationOrder`, `mergeHydratedSession`), but only for sessions that arrive **without** messages; the daemon's snapshot returns every message. Making the main window ask for summaries would need all of: (a) the companion window kept on full snapshots (it never hydrates: `if (... companion ...) return`), (b) the remote PWA and analytics unchanged, (c) `refresh()` (run after every send) to carry the already-loaded transcript of every session across a snapshot without a blank flash and without stale or missing messages relative to `snapshot.sequence`, with events applied in order, and (d) `applyEvent` to behave correctly for messages of a session that is not loaded. That is a UI state-machine change in a 4,000-line component that cannot be run or screenshot under this wave's rule, and a mistake would hide history, so it was not attempted. The cheap parts (indexes, `session_brief` on hot paths) are already in. Recommended next step, with tests allowed: a `summary` flag on `app.snapshot` plus a `loaded` carry-over keyed on `updatedAt` in `refresh()`.

## Cases left unknown or unverified (exact)
1. **Wake text identity.** The "already delivered" proof is the exact wake text in the Manager's transcript (the `blob_update` meta is not persisted). Two requests with the same bot name, kind and title, with a crash before the second's ack, make the second look `sent`: no duplicate, but its notice is skipped. A bot renamed between delivery and crash, or a deleted message, makes the lookup miss and the wake is offered again once (duplicate text, not duplicate work). Whether the UI can delete a single Manager message was not checked.
2. **Second request on a running assignment while its first wake is `pending`** is not announced by that call (the claim is refused so the older wake is not lost); nothing re-announces it later. The card stays in Needs you.
3. **A wake queued in memory when an approval is resolved** can still be delivered (no approval-resolution hook exists); it is a stale notice, not a duplicate. Questions are handled.
4. **A wake whose prompt path failed with a non-conflict error** is settled `sent` (the failure note is written to the Manager) and is not re-offered.
5. **Cancel window.** `adapter.cancel` cannot carry a turn id. After the gate is released and before the provider is asked, the turn can end and a queued prompt can start; the provider could then be asked to stop that newer turn. The row decision stays correct; whether a provider interrupt against a freshly started turn is harmless was not observed.
6. **`delivery_unknown` is conservative.** Activation failures (before the adapter was called), cancelled turns and provider-reported errors without `PromptAccepted` are all recorded as unconfirmed, so a replay of such a message needs `confirmResend` and an automatic retry of a retryable failure on such a turn is declined (auto-retry is off by default). The daemon stores no fact that proves "never invoked".
7. **The queue's `delivery_unknown` branch is unreachable today**: queue sends carry no `clientMessageId`, and queued prompts are deleted once accepted; a queued send whose turn later fails with unconfirmed delivery is shown by the failed turn, not by the queue row.
8. **The UI note on a failed turn depends on `delivery` being present in the turn JSON** the window receives. The storage column is `data.delivery`, but whether the session payload spreads it to `turn.delivery` was not run.
9. **Limited sessions:** the settle was read, not run; the interaction with a user prompt arriving in the same millisecond rests on the conditional UPDATE's WHERE clause.
10. **`delegation.paused`** emits no `settings.changed` event: an open Settings page keeps its old value until reopened. The setting's switch calls `settings.set`; against the old daemon in `D:\hz1` it will error with the daemon's message.
11. **Provider keeps-session** (round 1): still source-reading only, never run against Claude, Codex or OpenCode; the copy no longer promises success.
12. **Tests:** same stale storage test as in `REPORT.md`; round-2 lane reports list the tests that touch changed code (`cancel_while_starting_skips_prompt`, team delegation tests in `main.rs`, `team_p7_tests`, `team_p10_tests`, `haze_style_survives_a_document_round_trip`, `appearance_values_validate` and the retry/queue tests named there). `delegation_wake_claim` now takes a title and kind; no test caller was found.
