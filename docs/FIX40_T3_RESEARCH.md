## 1. Short summary: why T3 feels robust

1. **Intent is durable before work starts.** Every command is appended to an event log in one database transaction with its projections and outbox effects; the agent process is only a side effect after that (`docs/internals/overview.md:53-67`). A restart replays the log and retires or requeues the effects a dead process left behind (`apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts:68-77`).
2. **Resume is the default, and its failure has a defined, meaning-preserving fallback.** When a provider session cannot be resumed, it starts a fresh one and injects a bounded textual *handoff* of the app's own history instead of leaving the agent empty (`ProviderTurnStartService.ts:658-727`, `ContextHandoffService`).
3. **Every provider difference is a declared capability, not a guess.** Steering, queueing, rollback, fork, sub-agents and handoff are booleans per adapter; orchestration falls back explicitly (`packages/contracts/src/orchestrationV2.ts:207-234`, `docs/internals/adding-a-provider.md:22-37`).
4. **Nothing blocks the UI on a provider.** Persistent subscriptions with a snapshot+cursor, one retry owner with jittered backoff, and threads kept mounted while running so a running thread needs no replay (`docs/internals/connection-runtime.md:9-27,62-75`).
5. **Quota and rate limits are a first-class state, not a generic error.** A failed run is marked `usage_limit` with a reset time, the thread shows "Limited", and a scheduler sweep resumes it when the window opens (`UsageLimitRecoveryWorker.ts:10-71`, `ClaudeAdapterV2.ts:2749-2831`).
6. **Tests run the real thing.** The default test replays real provider transcripts through the real adapter, orchestrator, projections and persistence, replacing only the process boundary; several live tests drive real CLIs (`docs/orchestration-v2/testing-strategy.md:7-25`, `*.live.test.ts`).
7. **Plainly:** T3 is not robust because of a clever orchestrator. It is robust because state is durable, provider quirks are declared, resume always has a fallback, limits are visible, and the whole path is tested against real transcripts.

### Q2. Threads: what is stored where, and how live activity is shown

- **What a thread is.** The app thread is the user-visible conversation and the canonical history; runs are counted user-visible turns; execution nodes are the work tree inside a run; **provider threads are provider-native handles** that can be attached to app threads or nested nodes (`docs/orchestration-v2/README.md:62-81`). The app thread is the source of truth; a provider thread carries native/handoff *coverage* (`provider-switching-and-context.md:55-77`). Provider ids are never app identity (`README.md:33`).
- **What lives inside the CLI vs T3.** The provider keeps its native conversation (and its own tool state); T3 keeps events, runs, nodes, provider-thread refs, checkpoints (hidden Git refs) and handoff artifacts (`docs/internals/overview.md:82-85`; `README.md:56-58`).
- **Live activity in the UI.** Raw provider frames become normalized turn items and a conversation projection; the client subscribes to a bounded live stream, coalesces deltas, and keeps a running thread mounted so opening it needs no replay (`docs/internals/connection-runtime.md:62-75`; `ThreadLiveEventCoalescer.ts`, `LiveStreamBudget.ts`, `ThreadStream.ts`). Tool calls render as an expandable summary whose running output updates live (`docs/user/activity-log.md:1-6`).
- **Ours.** Conversations and sub-conversations exist (`team.rs:313` `list_blobs`, `team.rs:410` `message_blob`); the daemon is the owner of sessions. A sub-conversation with no turn renders the empty "Ready when you are." screen (`FIX39 R2:109`, `App.tsx:2483`). Mapping: T3 "app thread" ≈ our conversation; T3 "provider thread" ≈ the provider session id on our session row; T3 "execution node/subagent" ≈ our side conversation + delegate. We store the equivalent, but we do not model coverage or a live "waiting" state.

### Q3. Orchestrator V2: planning, delegation, isolation, reporting, steering, verification, watchdogs

- **Planning/delegation.** The orchestrator only serializes commands and decides events; an effect worker performs side effects (`README.md:53-67`). A model delegates with `delegate_task` (task, optional target/role, `mode: async|wait`, timeout, runtime/interaction mode) which creates an app-owned child thread + run; the child gets **only the task prompt**, never the parent's history (`orchestrator-mcp-server.md:210-257,430-450`). `create_threads` makes 1–20 ordinary threads sharing a checkout (`:312-336`).
- **Isolation.** Workspace is chosen per thread: `worktree` (new, with `baseRef`), `existing_worktree`, or `root`; `scratch:true` for no project (`orchestrator-mcp-server.md:338-352`; `ThreadLaunchService.ts:56-61`). Delegated children inherit the parent's project/branch/worktree (`:333-336`). Parallelism is inherent: many runs, each with its own provider session; the effect worker drains a fixed pool (default 4, `EffectWorker.ts:821`).
- **How sub-agents report back.** A terminal child run finalizes the parent's sub-agent projection; results return as a `subagent_result` **context transfer** plus a `delegate_task` wait result or later `task_status` (`orchestrator-mcp-server.md:430-475`). Child questions are routed to the parent as a notification (`:461-472`). Only the latest assistant content becomes the result; a failed run exposes the provider error first (`:474-475`).
- **Steering mid-run.** `t3_thread_send` modes: `auto` (start/steer/queue), `queue`, `steer` (needs a steerable turn), `restart` (interrupt-and-restart) (`:401-414`). Selection is capability-driven (`ThreadManagementService.ts:751-832`).
- **Verification/merge.** Diffs are derived from checkpoints, not provider notifications (`docs/internals/providers.md:156-158`); a revert coordinates workspace state with the provider and a provider that cannot rewind is rejected before touching files (`docs/internals/overview.md:82-85`). Merge-back is a delta context transfer (`thread-lineage-and-context-transfer.md:42-54`). Pull-request linking/settlement are server-owned (`docs/internals/overview.md:87-96`).
- **Watchdogs.** Recovery retire/requeue on startup/shutdown (`ProviderRuntimeRecoveryService.ts:68-77`); the scheduler ticks every 5 s and runs the usage-limit sweep (`Scheduler.ts:57`, `UsageLimitRecoveryWorker.ts:73-112`); durable continuation retries with backoff; the session reaper idle-releases at 30 min.
- **Ours.** The Manager delegates via `message_blob`/`assign_task` → `team::delegate` (`team.rs:416`); delivery queues against the side session if busy (`team.rs:573-581`); only `after_turn(side)` drains it (`team.rs:599-626`). Per-bot concurrency defaults to 1 (`storage lib.rs:276`), so a delegable bot's second conversation is queued against a session that never runs — stranded indefinitely (FIX39 R2:103-111; audit:130-137). The Manager is told "working on it" unconditionally (`team.rs:410` per FIX39 R2:110). We have no worktree isolation, no sub-agent result transfer, no coverage model.

### Q4. Steering: how a message sent while an agent works reaches it

- **T3, per provider** (`packages/contracts/src/orchestrationV2.ts:207-234`; adapter capability blocks):
  - Claude — `supportsActiveSteering: true`, `activeSteeringInterruptsTools: true`, `supportsSteeringByInterruptRestart: false` (`ClaudeAdapterV2.ts:287-290`).
  - Codex — `supportsActiveSteering: true`, `supportsSteeringByInterruptRestart: true` (`CodexAdapterV2.ts:254-256`).
  - OpenCode 1.x/2.x — active steering true, restart true (`provider-opencode/src/server/adapter.ts:142-144`, `.../v2/adapter.ts:102-104`).
  - Pi, Muse — active steering true (`provider-pi/src/server/adapter.ts:120-121`, `provider-muse/src/server/adapter.ts:120-121`).
  - ACP/Cursor/Grok — `supportsActiveSteering: false`, `supportsSteeringByInterruptRestart: true`, `supportsQueuedMessages: true` (`provider-acp/src/server/adapter.ts:423-425`, `provider-cursor/src/server/adapter.ts:105-107`).
  - The mode is chosen `auto`/`queue`/`steer`/`restart` (`ThreadManagementService.ts:764-781`), with a user default (Queue vs Steer) in Settings and `Cmd/Ctrl+Enter` to queue when the default steers (`docs/user/composer.md:54-63,195-209`). A queued message can be promoted to a steer (`orchestrationV2.ts:1274-1275,2850`). Capability refusals give honest copy: "…cannot redirect an active run. Stop it first…" (`UserFacingErrors.ts:12-19`).
- **Ours.** Codex steer and the queue exist (FIX39 R2/audit reference the queue and Stop); `session.model.update` returns `conflict` while a turn is active (`main.rs:2458` per FIX39 R2:148). We do not have a per-provider steering capability table; the behaviour differs by adapter without a declared model.

### Q5. Permissions: where the mode is decided and whether it can change mid-run

- **T3.** Permission mode is **per thread** ("Choose a mode in the message composer; it applies to that thread"), default per environment and overridable per project; **default is Full access** (`docs/user/permission-modes.md:3-16`). Mode is `thread.runtimeMode` resolved by `RuntimePolicy.ts:56-70`; a provider that lacks a mode runs it as `approval-required` (`adding-a-provider.md:28-33`). Session capability `supportsRuntimeModeSwitchInSession` exists (`orchestrationV2.ts:192-200`); a runtime-mode change is an orchestration command (`Orchestrator.ts:2222,3196,6629`), with an escalation ceiling when a caller (delegate/steer) tries to widen the target's mode (`orchestrator-mcp-server.md:479-487`).
- **Ours.** Permissions belong to the **bot** and apply to all its conversations (owner decision, `AGENTS.md`; FIX39_DECISIONS.md:29). The composer now writes the bot (item 16, merged). Side conversations have no permission control (composer replaced by "Close chat", `App.tsx:2525` per FIX39 R2:147); `session.model.update` conflicts mid-turn; the Manager could not change a sub-conversation's mode — though P7's `set_conversation_permission` proposal now exists (`crates/bloblex-daemon/src/proposals.rs:56`). A likely real cause of the friend's "paths still denied": a delegated task ran in the bot's workspace, not the named project (`proposals.rs:402-414` per FIX39 R2:152).

### Q6. Their MCP vs our bloblex bridge and the P7 tool set

- **Their MCP.** One authenticated HTTP endpoint `http://127.0.0.1:<port>/mcp` (server key `t3-code`), injected into each provider session with a per-session bearer credential scoped to environment/thread/instance/session, expiring and revoked on release (`orchestrator-mcp-server.md:29-56`). It exposes **eleven orchestration tools**: `orchestrator_capabilities`, `delegate_task`, `task_status`, `task_cancel`, `create_threads`, `t3_thread_launch`, `t3_thread_list`, `t3_thread_read`, `t3_thread_update`, `t3_thread_send`, `t3_thread_wait`, `t3_thread_interrupt` (`:193-428`). Privilege ceiling: a child/steered thread may never be broader than the caller (`:479-495`). Separately, **outside** agents (Claude Code, Codex, ChatGPT) connect to the same `/mcp` with OAuth + a one-time pairing code and a level (**Read only** default / Supervised / Full access); sign-in lasts 30 days and is revocable (`docs/user/outside-agents.md:1-95`).
- **Ours.** `bitbotsd mcp-bridge` is a stdio server launched by the provider CLI (`crates/bloblex-daemon/src/mcp_bridge.rs:1`); the Manager's current tools are `list_blobs`, `list_conversations`, `message_blob`, `schedule_task`, `list_my_schedules`, `list_projects`, `update_blob` (`team.rs:207-218`), plus proposal kinds (project/bot/task/permission). It is internal only, uses the per-session team token, and nothing is reachable from outside. The P7 owner decision extends this to a complete documented internal tool set; it is already partly built.

### Q7. Reliability engineering: what else makes T3 feel robust

- **Event model.** Event log is the source of truth; `EventSink` commits events, projections, the command receipt and outbox effects in one transaction; subscribers see events only after commit; duplicate command ids return the same receipt without re-running side effects (`docs/internals/overview.md:53-67`; `command receipts` `orchestration-v2/README.md:108`).
- **Turn completion vs follow-up work** are separate milestones; a late checkpoint cannot extend the recorded provider duration or keep the UI "working" (`overview.md:73-80`).
- **Persistence.** SQLite + migrations; V2 events must stay decodable on replay, and old environments are upgraded at startup (`overview.md:69-71`).
- **Tests against real CLIs.** The default integration test replays a **real provider transcript** through the real adapter/orchestrator/projections/persistence, replacing only the process boundary (`testing-strategy.md:7-25,62-105`); recorders exist (`bun run record:claude-replay`, etc., `:153-156`); gated **live** tests drive real binaries (`AcpRegistryOrchestratorV2.live.test.ts`, `CursorOrchestratorV2.live.test.ts`, `GrokOrchestratorV2.live.test.ts`, `OpenCode2OrchestratorV2.live.test.ts`). `adding-a-provider.md:70-102` is a list of real traps each with a required fixture.
- **Error copy.** Capability refusals are turned into provider-named sentences (`UserFacingErrors.ts:9-40`); generated UI text counts only successes and does not overclaim ("waiting is not finished; interrupt is not stopped", `activity-log.md:8-19`).
- **Ours.** We have a durable daemon DB, migrations, fake-adapter tests and the FIX39-owned test lists. We do not have transcript-replay integration tests or gated live tests.

## 4. What not to copy from T3

1. **Do not adopt the thread/run/execution-node graph as the user surface.** The owner prefers Bitbots' bots and visual UI over T3's threads. Take their *durability and fallback*, not their vocabulary. Evidence of the complexity you would inherit: `docs/orchestration-v2/README.md:62-81`, `core-graph-and-data-model.md`.
2. **Do not make provider switching or forks a first-class feature now.** It adds `ContextTransfer`/`ContextHandoff`/coverage tables and a fork lifecycle (`thread-lineage-and-context-transfer.md:259-271`) that the bots model does not need yet.
3. **Do not default permissions to Full access.** T3's initial default is Full access (`docs/user/permission-modes.md:8`); Bitbots' safety posture (Ask first, bots' permissions) is the opposite. Keep the owner's rule: permissions belong to the bot.
4. **Do not move permissions to the conversation.** T3 is per-thread; the owner decided per-bot (`FIX39_DECISIONS.md:29`). Our per-conversation control should write the bot (item 16), not introduce a per-thread mode.
5. **Do not build an outside-agents MCP endpoint reachable from the network.** T3's `/mcp` accepts external agents over OAuth (`docs/user/outside-agents.md`). The owner decided the Bitbots bridge is internal only (`FIX39_DECISIONS.md:24`) — an outside agent that can message your bots can run commands (prompt injection).
6. **Do not make steering a setting the user must understand.** T3 exposes Queue-vs-Steer defaults and keybindings (`docs/user/composer.md:54-63`). Keep `auto`: the manager steers when it can and queues otherwise, silently.
7. **Do not copy T3's event-sourced command/effect machinery wholesale.** Its guarantee comes from committing intent + projections + outbox in one transaction and replaying on restart (`overview.md:53-67`). We can get the visible benefits (recap, honest state, recovery) without a V2 rewrite; borrow the *invariants*, not the plumbing.
