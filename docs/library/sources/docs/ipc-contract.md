# Bitbots daemon IPC contract (v1)

> **What this is:** The daemon IPC contract (v1): methods, events, and the rules for the capability and the local listeners.
> **Status:** current
> **Last updated:** 2026-10-22

## Update commands

The desktop updater commands and events are defined in [docs/operations/updater.md](operations/updater.md). They run in the Tauri shell and persist preferences through the daemon settings store; they are separate from the daemon's v1 IPC methods below.

This is the integration contract between `bitbotsd.exe` and the desktop shell. The daemon is authoritative; UI state is reconstructed from `app.snapshot` and subsequent ordered events.

The desktop shell also exposes local Tauri commands for user-selected file flows. Native save/open dialogs retain their selected paths in process-local state and return only opaque single-use selection tokens to the webview. `write_selected_export_text` consumes a save token to write UTF-8 text, and `read_blob_import` consumes an open token to read UTF-8 JSON with a 64 KiB limit. A webview-supplied path is never accepted by these commands, and they do not access the daemon database.

This document includes intended contract requirements, not a statement that every guarantee is already implemented or independently tested. See [implementation status](operations/implementation-status.md) for open acceptance work. Snapshot/event atomicity, complete permission lifecycle, financial aggregation and process-tree cleanup remain under review.

## Transport and startup

The desktop shell owns the daemon child process and starts it for the signed-in Windows user. The daemon binds an ephemeral TCP port on `127.0.0.1` only. It must never bind `0.0.0.0`, a LAN interface, or IPv6 wildcard. On startup, the daemon writes one bootstrap JSON object to stdout before any logs:

```json
{"type":"bloblexd.ready","protocolVersion":1,"address":"127.0.0.1:49152","capability":"<random-256-bit-secret>"}
```

The capability exists only in daemon memory and the desktop shell's child-process channel; do not persist or log it. The shell keeps it in the native Tauri process and proxies renderer calls through Tauri commands. A connecting client must send it in `Authorization: Bearer <capability>`. Reject requests without a valid capability using a constant-time comparison. CORS is disabled. Only loopback peers are accepted. If another UI client is needed, it must receive the secret through the same authenticated native shell path.

**Remote mode (implemented in beta.30; Native added after it).** Remote adds one more listener and leaves the one above unchanged. While Remote is on, the daemon runs a second listener on `127.0.0.1:<remote.port>` (default 48620), published on the owner's tailnet with `tailscale serve --bg --https=443` (fallback 8443). It never binds a non-loopback address, never uses Tailscale Funnel and never runs `tailscale serve reset`. It calls `dispatch()` in-process and never reads, accepts or returns the capability. Its clients are paired devices authenticated by a cookie, not by the capability. The routes, pairing and policy are in [remote/PROTOCOL.md](remote/PROTOCOL.md). This exception needs the owner-approved AGENTS.md amendment ([remote/AGENTS_AMENDMENT_DRAFT.md](remote/AGENTS_AMENDMENT_DRAFT.md)). **Native (17 October 2026, owner amendment).** A second method, one at a time: while Native is on, the gateway's own listener binds the host's interfaces on `remote.nativePort` (default 48621) with TLS only, password sign-in plus the owner's approval per device, and abuse limits. It is the only non-loopback listener and never runs while Native is off; the daemon API below is unchanged. Details in [remote/PROTOCOL.md §13](remote/PROTOCOL.md).

HTTP transport uses WebSocket upgrade at `/v1/events` for push events and JSON over `POST /v1/rpc` for request/response. Immediately after upgrading, the shell sends `{"v":1,"afterSequence":<snapshot.sequence>}`. The daemon registers the live subscription before reading/replaying persisted events after that cursor; clients discard duplicate sequences. This closes the snapshot/subscribe race. On `replayAvailable:false`, fetch a fresh snapshot. Every response and event carries protocol version 1.

## Envelope

Requests:

```json
{"v":1,"id":"req_01","method":"app.snapshot","params":{}}
```

Responses:

```json
{"v":1,"id":"req_01","ok":true,"result":{"snapshotVersion":1,"sequence":0,"daemon":{"state":"ready"},"hosts":[],"runtimes":[],"agents":[],"sessions":[],"permissions":[],"usage":[],"budgets":[]}}
```

Errors:

```json
{"v":1,"id":"req_01","ok":false,"error":{"code":"invalid_argument","message":"The project path does not exist."}}
```

Events:

```json
{"v":1,"eventId":"evt_01","sequence":1,"timestamp":"2026-10-01T00:00:00Z","type":"runtime.changed","payload":{}}
```

`id` is an opaque string unique to the client request. Event `sequence` is daemon-global, monotonically increasing and persisted. Unknown fields and event types must be ignored by clients. No raw provider JSON appears in the UI contract.

### Durable prompt queue

`session.queue.*` stores prompts in Bitbots (never in the provider) and deletes each item once its prompt is accepted, so a sent item appears as an ordinary message. A queue item DTO is `{id,sessionId,text,attachments:[{name,path}],conversationRefs:[string],replyTo?:object,kind,dueAt:string|null,status,error:string|null,position:number,createdAt,lateBySecs?,meta?}`; `kind` is `user`, `send_later`, or the daemon-internal `retry`, and `status` is `queued`, `sending`, or `failed`. It holds only allowlisted prompt keys: `text`, `attachments`, `conversationRefs`, `replyTo`, plus the daemon-generated `meta` on `retry` items. Image attachments are re-validated at send time. A user RPC cannot set prompt `meta`; the daemon only accepts the `blob_message`/`blob_reply` team kinds and the `auto_retry` queue kind. Queue mutation RPCs return `not_found` for a missing or archived session and `read_only` for a side conversation.

After every finished turn the queue is drained once: a `turn.completed` on an idle session sends the next item (due scheduled items first, then plain items by position, then any pending team deliveries); a `turn.error` or `turn.cancelled` pauses the queue when items remain, so no prompt fires unexpectedly. Pause is in-memory and every session with queued plain items starts paused after a restart. Due `send_later` items are exempt from pause and fire from a one-second loop when their session is idle; a scheduled item that sends more than 60 seconds late appends an existing-style `notice` message, "Scheduled message sent N min late.", with meta `{"kind":"queue_late","lateBySecs":N*60}`. A send interrupted by a restart becomes `failed` with the message "Interrupted by a restart. Check the conversation before sending again." and is never auto-resent. Failed items stay until deleted or sent with `session.queue.send_now`.

### Automatic retry after overload and rate limits

> **Superseded in part by FIX39 (P8), see "FIX39 additions" below.** Overloaded retries are bounded at three attempts (`OVERLOADED_MAX_ATTEMPTS`, `crates/bloblex-daemon/src/retry.rs:16`), not five. Rate-limited failures now become the Limited state, with the reset time, and are not retried by this switch. The rest of this section still describes the beta.19 behaviour.

Opt-in via `experimental.autoRetry` (default false). With it off the daemon never schedules a retry and emits no retry notices or events. When on, a terminal turn error that carried an `overloaded` or `rateLimited` recovery hint and whose provider delivery was `acknowledged` may schedule one automatic retry: a `retry` queue item that sends the literal text `Please continue.` as a new turn in the same session, with the same locked model, effort and approval mode. A turn whose delivery is `unknown` always declines, because resending could charge a paid prompt twice. Overloaded backoff is `5s * 2^(attempt-1)` plus up to 100% jitter, up to 5 attempts. Rate-limited retries need a known reset: `max(reset of the provider's blocked quota windows) + 15s + 0..30s`, up to 2 attempts, and wait longer than `retry.maxWaitSecs` (default 21600, 0 to 86400; 0 means never wait for a window) declines. `authRequired` and hint-less failures stay silent. The decision is stored in `turns.data.retryDecision` as `{"decision":"retry"|"decline","reason":"<code>","at":"<rfc3339>"}`; reasons are `disabled`, `not_acknowledged`, `no_hint`, `auth_required`, `unknown_reset`, `too_long`, `max_attempts`, `superseded`, `pending_retry`, `session_unavailable`, or `cancelled`. Retry items bypass the queue pause and fire from the same due loop; a user prompt, a Stop, a model/effort change, or an archived/deleted session cancels any pending retry. After a restart a retry overdue by more than ten minutes is dropped with a notice "Automatic retry skipped because Bitbots was not running."

Schedule and decline notices use role `notice` with meta `{"kind":"auto_retry","status":"scheduled"|"declined"|"cancelled"|"skipped",...}`. Events: `turn.retry_scheduled` `{sessionId,turnId,itemId,retryKind:"overloaded"|"rate_limited",attempt,maxAttempts,runAt}`; `turn.retry_declined` `{sessionId,turnId?,reason}`. The eventual `auto_retry` user message carries `meta.kind == "auto_retry"` so the UI renders a notice instead of a bubble.

### Scheduled automations

Unattended work is fenced on every rail. A scheduler tick runs every 10 seconds (once at startup after restart recovery) and selects enabled automations whose `nextRunAt` is due, unless the global setting `automations.paused` (JSON boolean, default false) is true. `automations.maxConcurrent` (integer, default 1, 1–3) bounds simultaneous automation runs under the existing global cap of four turns. Missed occurrences coalesce into a single run: whatever the machine missed, at most one run starts and `nextRunAt` moves to the first occurrence strictly after now; a run starting more than 60 seconds late records `reason:"late:<secs>"`. An automation that already has a running run records a `skipped` run with `reason:"still_running"`. When the concurrency limit is reached or the blob already has a live user turn, the automation stays due for up to 15 minutes and is then recorded `skipped` with `reason:"busy"`.

An `Automation` is `{id,agentId,name,prompt,schedule:{kind,cron?,timezone,at?},sessionMode,approvalMode,maxRuntimeSecs,enabled,createdBy,nextRunAt,lastRunAt,consecutiveFailures,pauseReason,running,lastRun?}`. `scheduleKind` is `cron` or `once`; `sessionMode` is `new` or `reuse`; `approvalMode` is `plan` or `auto` only; `createdBy` is `user` or `agent`; `pauseReason` is `user`, `auto_failures`, `needs_approval`, or null. A `Run` is `{id,automationId,sessionId,status,reason,scheduledFor,startedAt,finishedAt}` where `status` is `running`, `completed`, `failed`, `skipped`, `cancelled`, `timeout`, or `interrupted`.

A run opens a normal blob session whose `link.kind` is `automation` (carrying `automationId`, `runId` and the clamped `approvalMode`), titled `Automation: <name>`, with the blob's model and effort pinned. The turn-end path maps outcomes onto the run: `turn.completed` -> `completed` and the failure counter resets; `turn.error` -> `failed`; `turn.cancelled` -> `cancelled`. After a failure of a run that only read things the automation retries after 1, 5 and then 15 minutes; on the fourth consecutive failure it is disabled with `pauseReason:"auto_failures"`. A run that changed something before it failed (a recorded file change, or any tool not on the read-only list: read, search, fetch, think, grep, glob, list, view, web search and fetch, todo) is never retried automatically: it is recorded with `reason:"error_after_changes"` (or `timeout_after_changes`), still counts as a failure, keeps its next scheduled occurrence, and the app offers **Retry now** (`automation.run_now`). A completed run whose whole reply is `(pass)` records `reason:"nothing_to_report"`; automation sessions are told they may end that way. The scheduler and `automation.run_now` claim an automation before starting it, so the two never open two conversations for one run. A run past its `maxRuntimeSecs` is cancelled through the provider and recorded `timeout`, counted as a failure. `once` automations disable themselves after their run. On startup, runs left `running` by an unclean exit become `interrupted` (not failures) and their sessions are untouched.

Safety rails: an automation session's effective approval mode is always `plan` or `auto`, regardless of the blob's `bypass` or the global default, and cannot be raised by `session.model.update`; a permission the classifier does not approve under `auto` is auto-denied with `permission.auto_denied {permissionId,sessionId,automationId,runId,category,summary}` and permission rows retain `resolvedBy:"policy:automation"`; structured questions are dismissed so the turn can finish. The MCP tool list for an automation session is empty, and `automation.*` write RPCs and scheduling tools reached through the MCP bridge return `forbidden`. A normal session's MCP tools add `schedule_task` (proposes a disabled automation with `pauseReason:"needs_approval"`, plan mode and `createdBy:"agent"`; it can never enable or run itself) and read-only `list_my_schedules`. Archiving or deleting a blob pauses (never deletes) its automations with `pauseReason:"user"`. Global pause stops new runs immediately and cancels nothing already running; cancelling one of its sessions through `session.cancel` sets its run `cancelled`.

Events: `automation.changed {automation}`, `automation.deleted {id}`, `automation.run.changed {run}`, `automation.run.finished {runId,automationId,agentId,sessionId,status,reason}`. Run `startedAt`, `scheduledFor` and `finishedAt` are RFC3339 UTC; `reason` is a short machine code (`late:<secs>`, `still_running`, `busy`, `error`, `error_after_changes`, `timeout`, `timeout_after_changes`, `nothing_to_report`, `session_error`, `cancelled`, `provider_error`) or safe sentence and never provider text.

### Memory and "about you"

Durable notes are stored in Bitbots (`memory_records` plus an FTS5 index over `title`, `body` and `tags`, and a `memory_versions` history kept to the ten newest versions per record). A `Memory` DTO is `{id,scope,scopeId,kind,title,body,tags,importance,pinned,origin,reviewed,sourceSessionId,version,createdAt,updatedAt,deletedAt}`. `scope` is `blob` (one agent's private notes), `project` (every blob in the project), or `shared` (everyone); `scopeId` is the agent id for `blob` and the project id for `project`, and null for `shared`. `kind` is `fact`, `preference`, `decision`, `procedure`, or `reference`. `origin` is `user` or `agent`.

The whole feature is off by default behind `experimental.memory` (JSON boolean). With it off no memory tools are listed and nothing is injected, but the `memory.*` RPCs still read for review and still accept user writes. `memory.sharedAgentWrites` (JSON boolean, default false) lets agents write `project` and `shared` notes; those stay `reviewed:0` and are never shown or injected until `memory.approve`. Agent-written `blob` notes are immediately `reviewed:1` but keep `origin:"agent"`. An automation-run session may only ever write `blob` scope.

Memory writes are untrusted input and share write rails: content carrying credential markers (`sk-`, `ghp_`, `AKIA`, `-----BEGIN`, `xox`, `Bearer `, long opaque runs, and the existing provider-error marker list) or injection-looking text (`<bloblex_` tags, "ignore … instructions", "disregard …", "you are now", "system prompt") is rejected with `invalid_argument`. Agent tool writes are capped at five per turn per session and bodies at 2000 characters.

While the feature is on, each turn may get a bounded summaries-only catalog appended to the **prompt text** (not the instructions), wrapped as `<bloblex_memory>…</bloblex_memory>`: reviewed, live records visible to the session (its own blob, its project, shared), pinned first then importance then `updatedAt`, each line `- [id8] <kind> · <title> — <first 100 chars of body>`, at most 3900 characters. It is re-sent only when its hash changes for that session or after a context change (compaction or a resume fallback). Because the block is part of the prompt and not the instructions, saving a memory never changes the instruction hash or forces a new provider thread, and the stored user message keeps the text exactly as typed. A session never sees another blob's private `blob` scope.

The MCP bridge adds `memory_search`, `memory_get`, `memory_write`, `memory_update`, and `memory_forget`, only while the feature is on and auto-allowed like the other `bloblex` tools. They return only reviewed records visible to the calling session. `memory_forget` soft-deletes and records `agent:<reason>` (at most 80 chars) in `memory_versions.changed_by`.

Persona: `profile.about` (string up to 1500 characters) is included in each blob's runtime instructions beside `profile.name` as `About the user (from their own notes): …`. Editing it is an explicit user change and does change the instruction hash (the per-blob persona remains the existing `instructions` field).

Events: `memory.changed {record}` and `memory.deleted {id}`.

### FIX39 additions (18 October 2026)

Names and shapes come from the package reports (`docs/FIX39_P<n>_REPORT.md`) and the code. No new event name was added in this wave; several existing payloads gained fields.

**Settings keys** (`settings.set` validates each; anything outside the allowlist is refused):

- `concurrency.botsAtOnce`: integer 1 to 16, default 4. The one limit on bots working at once. It replaces the per-bot cap, which is no longer enforced, although `agents.maxConcurrency` is still stored. `runtime.capabilities` reports it as `globalConcurrency.limit`.
- `experimental.resumeAfterUsageLimits`: JSON boolean, default on (an absent key means on). Resumes a Limited conversation when its window opens. With it off the conversation waits for you.
- `experimental.autoRetry`: unchanged, default off. It now covers transient failures only (overloaded, a dropped stream, a process that fails to start), with up to three attempts. Rate-limited failures become the Limited state below and are no longer retried by this switch.
- `diagnostics.logLevel`: `info` (default) or `debug`. Hidden in the UI. It takes effect at the next daemon start, and dependencies stay at `info`.
- `composer.busySendMode`: `steer` (default) or `queue`. What a send does while a bot works. Steer is used only where `runtime.capabilities` reports steering; otherwise the composer queues and says so.
- `exec_gate.codex.steer` is seeded open. A one-time migration opens an existing closed gate once. `session.steer` refuses only a provider whose adapter cannot steer; today that is every provider except Codex, and those answer `unsupported`.
- `experimental.sidebarModel` and `experimental.botLock` are the two new Experimental features, stored like the others under `experimental.<name>`.

**Remote status** (`remote.status`): `tailscale` also reports `starting` and `not_running`. `remote.enable` on a port that another Bitbots copy already serves is refused with `conflict`. A port held by another program moves the gateway to the next free loopback port (the configured port, then +1 to +9 skipping the Native port, then an OS-assigned port), and the chosen port is saved as `remote.port`.

**Limits and turn errors.**

- A session in a usage or rate limit has `state: "limited"` and `limitedUntil` (RFC 3339, or null when the provider gave no reset time). `limitedUntil` appears in `session.list`, `session.get` and `session.changed`. With no reset time the conversation stays limited and asks you; it never retries on an unknown window.
- `turn.error` carries `state` (for example `limited`) and `recoveryHandled: true` when a retry or continuation has already been scheduled for that turn. Clients hide those turn errors. The retry events are the ones from beta.19 (`turn.retry_scheduled`, `turn.retry_declined`).
- Notices: "Limited until <time>. I'll pick up when the window opens.", "Retrying (n of 3)…", and "Picking up where it left off" before a one-off `Continue where you left off.` prompt. A continuation follows a restart, a provider crash or a timeout, and at most three recoveries run per conversation.
- A lost session gets a summary. When a resume fails or a model changes, the next prompt carries one bounded `<bloblex_recap>` block: the last eight user and assistant messages (600 characters each), up to 12 changed file paths, 6000 characters in all. It is added to that one prompt, is never stored or logged, and the notice reads "Started a fresh session. The agent was given a summary of the conversation."

**Locks** (`agent.lock.set`). While a bot is locked these refuse with "This bot is locked. Unlock it to change its settings.": `agent.update`, `agent.delete`, `agent.restore`; `agent.team.update` when the project, role or leader would change (including to Unassigned); `project.delete` while a locked bot is in that project; `session.model.update` except `planMode`; `session.permissions.set`; the Manager's `update_blob`; approval of a Manager permission proposal; and the legacy model migration. Still allowed: unlocking, `agent.create`, hiding and sort order, `planMode`, and every read.

**Tags.** `project.update` and `agent.team.update` accept `tags`: an array of strings, trimmed and lower-cased, 1 to 24 characters each, at most 8, de-duplicated. `[]` clears them. The Manager's tag changes go through approval; a locked bot refuses a tag change.

**Merge proposals** (P10). A coding task that shares its repository with another working task runs in its own git worktree, beside the repository, on a `bitbots/<slug>` branch. A researcher-tagged or researcher-role bot never gets one. When the task completes, a proposal of kind `merge` offers the merge. `proposal.decide` with `approve` merges (fast-forward, else a merge commit; never forced) and removes the copy and branch. `reject` keeps the branch unless `discard: true` is sent, which removes the copy and branch. Merge and discard are refused while the task is still working, and a dirty main checkout refuses a merge with the proposal left pending. Remote devices with operator tier can send `discard` when approvals from remote are on (see [remote/THREAT_MODEL.md](remote/THREAT_MODEL.md) §14).

**Manager tool set** (P5, P7). These are tools on the local MCP bridge, not daemon RPC methods, and ordinary bots do not get them. Read tools need no approval: `list_blobs`, `read_blob`, `list_projects`, `read_project`, `project_status`, `list_conversations`, `read_conversation` and `get_conversation_permission`. Change tools create a proposal that waits for owner approval: `propose_bot`, `update_blob` (name, description, role, instructions, tags, look, model, effort and permission; never Full access), `propose_project`, `update_project`, `assign_task` (a brief, a done goal and a report-back are required), `message_blob`, `start_conversation`, `open_conversation` and `set_conversation_permission` (only `ask` or `auto`, and only for a side conversation the Manager started). `ask_user` is unchanged. Proposal kinds now stored are `bot`, `project`, `task`, `open`, `permission`, `merge`, plus the FIX36 `playbook` and `profile`. Decisions emit `proposal.changed {id,kind,sessionId,status,result,decidedAt}` with `status` `approved`, `rejected` or `expired`, and `permission.resolved`.

**Tool steps** (P2). A tool step may carry a short `label`, and a `pattern`, `url` or `path` where the provider gave one. Remote devices do not receive these fields by default (see [remote/PROTOCOL.md](remote/PROTOCOL.md) §7).

**Working bots** (P9) is a UI panel built from side sessions, queued notices and turn state. It adds no RPC.

### T3 additions (26 October 2026)

All of these are loopback-only and `class: "never"` in `apps/desktop/src/remote/tiers.json`: none is reachable from a paired phone.

- `media.preview { sessionId, path }` returns `{ status: ok|unavailable|unsupported|blocked|tooLarge, reason, name, relativePath, kind: image|audio|video|pdf|text|unsupported, mediaType, size, dataUrl, text, truncated, language }`. The root is the conversation's `projectPath` only. The path is checked as text, a symlinked leaf is refused, the canonical target must stay inside the canonical root, secret-like names (`.git`, `node_modules`, `.env*`, key files, `auth.json`, ...) are refused, the extension must be on the allowlist and the bytes must match it. A refusal is a normal reply with a `status`; only a bad request or unknown conversation is an error. **`{ sessionId, mediaId }` instead of `path`** reads the exact file a generated-image record stores (Phase 2 below).
- `session.checkpoints { sessionId }` returns `{ capability: { fileUndo, fileUndoReason, providerStateRestore: false, providerReason }, busy, turns: [{ turnId, files: [{ id, turnId, path, operation, additions, deletions, state: available|reverted|blocked, reason, diffComplete }] }] }`. `state` comes from a dry run (`git apply --reverse --check`, the same validation `file.revert` uses) on the newest 200 changes. Read-only. There is no whole-turn restore: undo is one file at a time through `file.revert`, which checks and applies in one call and which Git itself refuses when the file no longer matches. Undoing a file never changes what the agent remembers.
- `session.workspace { sessionId }` returns `{ mode: shared|isolated|unknown, projectPath, isGit, repoRoot, branch, head, worktree, isolationFailure, sharedWith }`. `isolated` only when the conversation's own worktree is its working folder; `isolationFailure` is the one-line reason stored as `link.worktreeError` when a separate copy was tried and failed.
- `delegation.cancel { delegationId }` and `delegation.cancelGroup { originSessionId, originTurnId | delegationIds }`: a queued brief is withdrawn and never delivered; a running assignment has its teammate's turn cancelled (only when that turn is the assignment's own) and ends through the normal turn-end path; terminal rows come back unchanged; the Manager's own turn is never cancelled.
- `delegation.updated` rows are unchanged on the wire. A teammate's pending approval (and, if side conversations are ever allowed to ask, a question) wakes its Manager once per request: the Manager receives a `blob_update` message (`meta: { kind, fromAgentId, fromName, sideSessionId, delegationId, requestId, requestKind: approval|question, title }`, text starting `[Update from NAME]`). It carries the request's short title only, never the command, diff or tool input. The request can only be answered by the owner in the teammate's conversation; the Manager has no method to answer it. The claim is durable (`wake_request` on the ledger row), so a restart does not repeat it.
- **A delegated bot can ask the owner a question** (`ask_user` in a side conversation, 26 October 2026). Allowed only when the side conversation's origin chain (four hops at most) is attended: archived conversations, scheduled and unattended runs, and side conversations started by one still refuse it. The card is the teammate's own; only the owner can answer it, and the answer goes only to the session on the card (never a caller-supplied id). While a question is pending, the teammate's turn ending does not complete the assignment and sends no `[Reply from X]`; the answer's (or the dismissal's, or the expiry prompt's) next turn is adopted by the same row and ends it. The Manager is woken once (the `blob_update` above) and later gets one non-waking notice (`meta.kind: question_resolved`, outcome answered, dismissed, expired or closed) with no question, option or answer text. Cancelling or ending the assignment closes its pending cards as dismissed without prompting the child (`permission.resolved` with `status: cancelled`); answering a card whose assignment already ended returns `conflict` and closes it. Known race: an answer given in the last moments of the question turn can be queued while that turn completes the assignment, so the child's follow-up is no longer relayed to the Manager.
- Delegation ledger invariants: a turn that ends before `started` is recorded is finished from the turn's stored outcome (the started/terminal race); one brief and one reply per `delegationId` are ever queued; a cancelled brief that reaches the front of the queue is dropped; `delegation.cancelGroup` also accepts `delegationIds` and answers with only the rows it was about; `reply_state` (`pending`/`delivered`, not on the wire) makes the `[Reply from X]` relay once per outcome and lets a completed row's reply be offered again after a restart. Completed, failed and cancelled replies are offered again after a restart (the failed text is rebuilt from the row's stored error); interrupted assignments send no reply.

Terminals are not daemon methods. They are native Tauri commands in the main window only (`terminal_open`, `terminal_write`, `terminal_resize`, `terminal_close`, `terminal_list`; events `terminal://output` and `terminal://exit` emitted to `main` only), so they never cross the daemon API or the remote gateway.

Not in backups and not on the MCP.
- **From a provider.** New adapter event `ImageRequested { tool_call_id, stem, saved_path, inline_base64, failure }`; at most one of the last four is set. `inline_base64` is Codex's `result` and is stripped before anything stores or forwards the event. On arrival, in this order: a `saved_path` must be absolute, a regular file (not a symlink), not empty, at most 20 MiB, `.png`/`.jpg`/`.jpeg`/`.webp`/`.gif` with matching bytes → `ready`; `inline_base64` is decoded, capped at 20 MiB, typed by its own bytes and written to `<data>/generated/<session id>/<media id>.<ext>` → `ready`, anything else is `failed`; an absolute `stem` → `pending` (a relative one records nothing); `failure` → `failed` with a one-line reason. None of this needs an active turn, and none of it changes session state or wakes anything.
- **The sweep.** The daemon looks at the pending rows every 2 seconds (one indexed read when there are none; stops on shutdown; rows are stored, so a restart resumes). First of `<stem>.png`, `.jpg`, `.webp`, `.gif` that is a regular file (not a symlink), non-empty, at most 20 MiB, modified at or after the request minus 5 s of clock slack, with bytes matching the format, and the same size on two passes in a row → `ready`. Nothing after 35 minutes → `failed`, "The image didn't arrive."
- **The transcript.** One message per record, `id` equal to the media id, role `notice`, stored with no turn and rewritten in place: `meta {kind:"generated_image", mediaId, status, name, bytes, mediaType, provider, detail}` (no path, no bytes). Text: `Generating an image…`, `Generated an image: <name>`, `The image couldn't be generated: <detail>`. Every change emits `message.completed` with `{sessionId, messageId, role:"notice", message}` (no `turnId` at the top level), then `session.changed`, then `media.generated {sessionId, mediaId, status}`.
- **`media.preview { sessionId, mediaId }`** (new parameter, used instead of `path`; both together is `invalid_argument`). The row must belong to the conversation and be `ready`, else `status: "unavailable"`; only the path stored on that row is read. A symlink leaf is `blocked`, a regular non-empty file of at most 20 MiB is required (`tooLarge` beyond), only `.png`/`.jpg`/`.jpeg`/`.webp`/`.gif` with matching bytes (no SVG), and a file that is gone is `unavailable` "That file is no longer there.". The reply is the usual shape with `kind:"image"`, `relativePath: null` and `name` as the file name only; it never carries the folder. **With `path` nothing changes**, including the project-folder rule: a generated file's own path outside the project is still `blocked`.
- **`media.reveal { sessionId, mediaId }`** → `{status, revealed, reason}`: for a `ready` record the daemon opens the file's folder with the file selected (one fixed program and one fixed argument, no shell); anything else is `unavailable` with `revealed: false`. Not on the MCP.
- **`runtime.capabilities`** gains a top-level `generatesImages: boolean`: true for Codex, false for Claude Code, and false for OpenCode, whose ACP surface (models, effort and mode in `configOptions`) says nothing about image models; a bot that uses the tool anyway still gets its card and record.
- **MCP.** `read_conversation` adds `mediaId` and `status` to a generated-image notice, with no path and no bytes.
- **Desktop.** `save_generated_image { sessionId, mediaId }` → `bool`: one native call that reads the image through `media.preview`, offers the save dialog with the file's own name and a filter for its type, and writes only the path the owner picked; `false` means cancelled, and a refused preview returns its `reason`. The renderer never supplies a path.

### Phase 3: review (31 October 2026): diff, stage, revert, pull requests

Every method below is desktop only: `tiers.json` rows are `never`, none emits a new event, and none is on the Bitbots MCP. The client never supplies a folder: each call names a conversation and the folder comes from the stored row. Every git and `gh` command is an argument list with no shell and a time limit, with `GIT_TERMINAL_PROMPT=0`; paths go to git with `--literal-pathspecs`; the daemon never reads, passes or prints a credential, and no path, file content or git output is logged. **Omitted and explicit `null` are the same.**

- **`session.repository`** gains `staged: "none" | "partial" | "all"` on each file, from the porcelain v2 `XY` field (`X` set and `Y` clear is `all`, both set is `partial`, otherwise `none`; an untracked file is `none`). Nothing else in the reply changes.
- **`session.git.diff { sessionId, repositoryPath }`** → `{ repositoryPath, previousPath, change, diff, truncated, binary, addedLines, removedLines, staged }`: one file's whole diff against `HEAD`, capped at 2 MiB (`truncated`). An untracked file (or any file before the first commit) gets the synthesised added-file diff `session.repository` builds, with the larger cap; its line counts are `null` when it was cut. A path with no changes answers `diff: null` (and `change: null`), not an error.
- **`session.git.stage { sessionId, paths, staged }`** → `{ files }` (the `session.repository` list). `paths` is 1 to 200 repository paths, each in the current status list; any other path is `invalid_argument`, "That file has no changes.", and nothing is applied. A rename's previous path is staged or unstaged with it. `staged: true` runs `git add --`; `false` runs `git restore --staged --`, or `git rm --cached --` in a repository with no commits.
- **`session.git.revert { sessionId, repositoryPath, confirm }`** → `{ undoId, name, files }`. Order: `confirm: true` (else `invalid_argument`); `conflict`, "A bot is working in this folder. Stop it or wait, then try again.", while any conversation (this one included) is working in the folder; the path must be exactly in the current status list (else `invalid_argument`), and a submodule, link or directory is refused with a plain sentence; **then the safety copy**, and only then the discard. The copy goes to `<data>/reverted/<undo id>/` (`content`, `meta.json` with `{sessionId, repositoryPath, createdAt}`) and is size-checked; over 20 MiB is refused ("That file is too large to keep a copy of, so Bitbots won't discard it."), and a failed copy discards nothing ("Bitbots couldn't keep a copy of that file, so it didn't discard it."). Discard: tracked modified or deleted: `git restore --source=HEAD --staged --worktree --`; renamed: the same for the previous path, then the new path leaves the index and the disk; added to the index but not in `HEAD`: `git rm --cached --`, then the file is deleted; untracked: the file is deleted. `undoId` is `null` when there was no file to copy (a deleted file).
- **`session.git.revertUndo { sessionId, undoId }`** → `{ files }`. The record must belong to the conversation, else `not_found`. If the path is in the status list again, or a file there is not tracked by git, `conflict`, "That file has changed since, so Bitbots won't overwrite it." It restores the working file only, not the staged state, then deletes the copy. The daemon deletes copies older than 7 days at startup.
- **`session.pr.draft { sessionId }`** → `{ ready, reason, gh: { available, login }, repoRoot, branch, base, isWorktree, remote, commitsAhead, uncommitted, title, body, existingUrl }`. `ready: false` gives the first applicable `reason`, in this order: not in a git repository; on a detached commit; on the base branch ("Pull requests need their own branch. This conversation is on `<branch>`."); no `origin` remote; the GitHub CLI not installed; not signed in; nothing to propose yet. `base` is the link's `worktree.base`, else `refs/remotes/origin/HEAD`, else `null`. `commitsAhead` is against `origin/<base>` (else the local `<base>`); with no known base it counts commits on no remote. `remote` is the literal `origin` or `null`; its address is never returned. `title` is the subject of a single commit ahead, else the conversation title, at most 72 characters. `body` is "## Changes" (up to 20 commit subjects), "## Files" ("N files, +a −r"), "Made with Bitbots."; no conversation text. `existingUrl` comes from `gh pr view --json url,state` (10 seconds) when the state is `OPEN`, else `null`.
- **`session.pr.create { sessionId, title, body, base, draft, commitMessage, confirm }`** → `{ steps, url }`. Needs `confirm: true`; `title` 1 to 256 characters; `body` up to 60,000; `base` a plain branch name or `null`. It re-runs the draft's checks (`invalid_argument` with the reason), refuses while a bot is working in the folder (`conflict`), and refuses to start with no commits and no `commitMessage`. Steps, each `{ id, status: "done"|"failed"|"skipped", detail }`, a failed step stops the rest and what worked stays: `commit` (`commitMessage` non-empty: commit everything; otherwise skipped and uncommitted files stay out), `push` (`git push -u origin refs/heads/<branch>:refs/heads/<branch>`: never forced, never the base), `pr` (`gh pr create --head <branch> --title <title> --body-file - [--base <base>] [--draft]`, the body on stdin). `url` is the first `https://` address the command printed, else `null` with the step failed. On success one notice is added to the conversation, "Opened a pull request: <url>", with `meta {kind: "pull_request", url, title}`.

### Phase 3: projects (31 October 2026)

Git work the owner could not reach before: the task copies nothing uses any more, worktree setup files and submodules, cloning and discovering repositories, and searching a project. Every method below is `never` in `tiers.json`, and the one event, `project.clone.changed`, is `drop`; none is on the Bitbots MCP. The client never supplies a folder for a git action: it names a conversation, a project or an opaque id, and the folder comes from the stored row. Only `project.clone.parent` and `project.discover.folder` are paths, and they come from the native folder picker. Every command is an argument list with no shell, has a time limit, sets `GIT_TERMINAL_PROMPT=0`, uses git's and `gh`'s own sign-in and never reads, passes or prints a credential.

- **Abandoned worktrees.** `worktree.abandoned {}` → `{items: [{id, repo, path, branch, reason, dirtyFiles, commitsAhead, lastActivityAt}]}`. Repositories scanned: the repo roots of registered projects and of every conversation's `link.worktree.repo`; for each, `git worktree list --porcelain`, keeping an entry only when its path is inside `<repo>-bitbots` and its branch starts `bitbots/`. The main worktree and locked entries are skipped, as is any copy a non-archived conversation works in (its folder is the conversation's folder or its `link.worktree.path`, whatever its state) and any registered project's own folder. `reason` is `folder_missing` (the folder is gone), else `conversation_archived` (only an archived conversation points at it), else `conversation_deleted`. `id` is a 16-character FNV-1a hash of the normalised path; `dirtyFiles` counts `git status --porcelain` entries (0 when the folder is missing); `commitsAhead` is `git rev-list --count HEAD..refs/heads/<branch>` in the main worktree; `lastActivityAt` is the worktree folder's modification time (RFC 3339, null when unreadable). Nothing runs on a timer.
- **Removing one.** `worktree.removeAbandoned {id, deleteBranch, force, confirm}`: no `confirm: true` is `invalid_argument`, "Confirm removing the worktree first."; the list is recomputed and an id not on it is `not_found`, "That worktree is no longer on the list." — so a live conversation's copy, a project's own folder or any folder this daemon did not list is refused with nothing changed. Uncommitted files, or `deleteBranch` with commits ahead, need `force: true`, else `conflict` naming what would be lost ("2 uncommitted files and 3 commits would be lost."). `folder_missing` runs `git worktree prune`; anything else runs `git worktree remove [--force] <path>`. `deleteBranch` then runs `git branch -D <branch>` and removes nothing else. Reply `{removed, branchDeleted, detail}`: `removed` is true only when the folder is gone (or the stale record was pruned), and `detail` is one plain sentence.
- **Setup files and submodules.** A project's `overrides` gain `copyFiles: string[]` and `initSubmodules: boolean`; a project with neither stored reads as `[]` and `false`, and every project DTO carries both keys. `copyFiles` is at most 50 entries, each a relative path of at most 260 characters with no `..` segment, drive, wildcard, leading slash or control character; `initSubmodules` is a boolean. Both are validated in `validate_project_overrides`, so `project.update` refuses them otherwise, `Storage::project_update` still refuses the whole `overrides` key, and the desktop-only outlets of `setupScript` apply unchanged: never in a backup, never to a device. They run only for a conversation in its own worktree (not the project's folder), once, before its first turn, in the order copy, submodules, script; the setup flag covers all three. **Copy:** each file comes from the project's folder to the worktree, and a source must be a regular file, not a symlink, of at most 20 MiB; a missing source is skipped and named, a link or an oversized file fails the step, and an existing target is never overwritten. **Submodules:** `git -C <worktree> submodule update --init --recursive`, with the setup script's time limit, and Stop cancels the setup as it does for the script (`Setup::Cancelled`). **Notices** keep `kind: "setup_script"`: a running line, then one line such as "Copied 2 files and set up submodules." with `meta.copied` and `meta.skipped` holding names only (never contents) and `meta.status`/`meta.detail` as before. A failure reports like a failed script — "Setting up this project failed: <detail>" and "Setting up this project failed in this worktree: <detail>" to the agent — and the turn continues the same way. A project with only a script keeps its earlier wording exactly.
- **Clone.** `project.clone {url, parent, name, confirm}` → `{job}` at once; the job is `{id, url, target, state: "running"|"done"|"failed"|"cancelled", detail, project}` and every change emits `project.clone.changed {job}` (`drop` for devices). No `confirm: true` is `invalid_argument`, "Confirm cloning the repository first.". **The URL is untrusted input:** only `https://`, `ssh://` and the `git@host:path` form are accepted; a leading `-`, an `ext::` transport, `file:`, `http://`, an address with whitespace or a control character, and any URL holding a password are refused before git starts ("Put no password in the URL. Sign in with git or the GitHub CLI instead."). `parent` must be an existing absolute folder; `name` defaults to the URL's last segment without `.git` and is checked as a Windows folder name; an existing target is `conflict`, "That folder already exists.". The clone is `git -c protocol.ext.allow=never clone --no-recurse-submodules -- <url> <target>`, shell-free, 30 minutes, `GIT_TERMINAL_PROMPT=0`, git's own sign-in. On success the folder is registered through `project.create` and `project` carries it; on a failure or a cancel the folder is removed **only if this job made it** (an empty folder or one with the clone's own `.git`; anything else is left alone). `project.clone.cancel {id}` stops git's whole tree (`taskkill /T /F`); `project.clone.list {}` → `{jobs}` newest first, in memory only (the last 20), so a window that reopens still sees them.
- **Discover.** `project.discover {folder, depth}` → `{folder, repos: [{path, name, branch, alreadyAdded}], truncated}`: `folder` is an existing absolute folder, `depth` defaults to 3 and is capped at 5. Off the runtime, in 10 seconds, at most 5,000 folders and 200 repositories (`truncated` when a limit stops it). It never follows a symlink, skips hidden folders and `node_modules`, `target`, `dist`, `vendor` and `*-bitbots`, and stops going down at a repository, so a project's submodules are not offered as projects of their own. `branch` is null on a detached commit; `alreadyAdded` compares with `worktree::normalize`, and a registered project's own folder is listed with `alreadyAdded: true`.
- **`projects.folder`** is a new setting: a string, empty or an absolute folder path (at most 1,024 characters), validated in both layers and in the `settings.set` key list. It is refused by `exportable_setting`, because a folder path belongs to one machine.
- **File search.** `project.files.search {sessionId?, projectId?, query, limit}` → `{files: [{path, name, score, matches}], truncated, source: "git"|"walk"}`. Either a conversation or a project names the folder (a conversation first); neither, an unknown id, or a target with no folder answers `{files: [], truncated: false}`. `path` is relative with forward slashes, `matches` the character indexes of the query in `path`, `score` the ranking weight. `query` is cut to 200 characters, `limit` defaults to 20 and is capped at 50. The list is `git ls-files -co --exclude-standard` in a repository (so `.gitignore` applies and untracked files are included) and a walk that skips hidden, build and `*-bitbots` folders otherwise; at most 50,000 files, reused for 15 seconds per folder. A fuzzy subsequence match, with a bonus for the file name, a run of characters and the start of a segment; an empty query gives the shortest paths first. A file whose name says it holds a secret (`media::names_a_secret`) is left out.
- **Content search.** `project.content.search {sessionId?, projectId?, query, caseSensitive, regex, limit}` → `{results: [{path, line, preview}], truncated, source, reason}`. `query` is 1 to 200 characters, else `invalid_argument`; `limit` defaults to 100 and is capped at 500; `preview` is the line trimmed to 200 characters. In a repository: `git grep --no-color -n -I --untracked --exclude-standard [-i] [-F|-E] -e <query> --`, off the runtime, 10 seconds, keeping whatever it printed with `truncated: true`. Otherwise a walk with the same skips, text files of at most 1 MiB and at most 5,000 files. A pattern that is not a valid regular expression answers `{results: [], reason: "That isn't a valid search pattern."}` and nothing runs; the query is literal unless `regex` is true. Results from secret-named files, and binaries, are left out.

### Phase 4: projects (31 October 2026)

A project can name the repository it holds, so a conversation handed over from another machine lands in the same code. `repoIdentity` is `host/path` — `github.com/owner/repo` — with the host always lower case and the path lower case only on GitHub, GitLab and Bitbucket; a non-default port stays (`git.example.com:8443/team/app`), and a local path, a `file:` URL or an unknown scheme gives `null`. **A remote URL can hold a credential, so one never reaches the column, a reply, a device or a log:** the identity is a host and a path only, and the address that travels (`handoff.preview.repo.url`) has any user and password removed, except the literal `git@host:path` form, which carries neither — a query and a fragment are dropped too. The identity is read from the project's own folder with `git remote get-url origin` (no shell, `GIT_TERMINAL_PROMPT=0`, 5 seconds, off the runtime) when the project is created or cloned, when its settings change (`path`, `name`, `description`, `tags` or `overrides` — never a sidebar collapse), and once for every project at startup; **`project.list` never runs git.** The column is added by an additive migration in `ensure_team_schema`.

- **`project.list` and `project.get` rows** gain `repoIdentity: string | null`. It crosses to devices: no redaction rule drops it, and it never holds a credential.
- **Find by identity.** `project.findByIdentity { identity }` → `{ project }` or `{ project: null }`: the first project (in `project.list` order) whose identity matches and whose folder is there, so a project whose copy was deleted never wins. The host compares case-insensitively. A missing, blank or over-400-character identity is `invalid_argument`. It runs no git. `tiers.json` class `never` (a desktop action), no event, not on the Bitbots MCP.
- **`.bitbots.json`.** An optional file in a project folder's root, committed by the owner: `{version: 1, setupScript, defaultBot, approvalMode}`. **A repository is someone else's input, so the file does nothing until the owner trusts that exact content.** It is read from the project's own folder (never a conversation's copy), must be a regular file, not a link, of at most 64 KiB, and `hash` is the SHA-256 of its bytes. `state` is `none` (no file), `invalid` (not JSON, or a `version` other than 1 — nothing in it is used), `untrusted` or `trusted`. A bad field is dropped and named in `problems` while the rest stands, an unknown key is named and ignored, and **`approvalMode: "bypass"` is refused** ("A repository file can't turn on Full access."). `settings` is `{setupScript, approvalMode, defaultBot}`, or `null` when the file is invalid.
- **`project.sharedSettings.get { projectId }`** → `{found, valid, problems, settings, hash, trusted, state}`.
- **Trust.** `project.sharedSettings.trust { projectId, hash, confirm }`: no `confirm: true` is `invalid_argument`; a `hash` that is not the file's current hash is `conflict`, "That file has changed. Check it again." The hash is stored in the project's `overrides.trustedSharedHash`, so it has the overrides' outlets: a backup carries no projects at all, and a device never sees the key (it is dropped wherever it sits). A settings save that does not name the file keeps the trust; `project.sharedSettings.untrust { projectId }` clears it. Both reply as `.get`.
- **`project.sharedSettings.write { projectId, replace, confirm }`** writes the project's own `setupScript` and `approvalMode` overrides (Full access left out) and the `defaultBot` the file already names, beside the file and then renames it, trusts the new hash and commits nothing. An existing file without `replace: true` is `conflict`. Reply as `.get`.
- **One resolver.** `effective_overrides(st, project)`: the project's own override wins, field by field, then a trusted file, so a file whose hash no longer matches stops counting at once. `project_setup.rs` (the setup script, the copied files and submodules), the turn's approval decision (`exec_options_for_session`) and `projectApprovalMode` on `session.list` and `session.get` all read through it. A `session.changed` payload keeps the stored value until the next read.
- **`project.list` rows** gain `sharedSettings: "none" | "untrusted" | "trusted" | "invalid"` and `defaultBot: {name, agentId} | null` from a trusted file (`agentId` is `null` when no bot here has that name). Reading the file is one stat per project, cached by modification time and size, and `project.list` still runs no git.

Budget admission, pause, cancellation, and provider acknowledgment remain authoritative over policy decisions.

Execution snapshots are returned as `{id,sessionId,turnId,agentId,runtimeId,provider,createdAt,requested,applied,evidence,instructionSha256,adapterFlags,status}`. `requested` contains only setting values that are safe to retain, `instructionsPresent`, `maxConcurrency`, and custom environment key names; it never contains instruction text or environment values. Status is `applied`, `partial`, `rejected`, or `runtime_default`. Session baselines are `claudeInstructionSha256` (last Claude instruction hash proven applied), `codexThreadInstructionSha256` (instructions installed when the current Codex thread started), and `opencodeCostTotal` (exact cumulative USD cost as decimal text). Usage rows include nullable `execSnapshotId`, `providerUpdateId`, `usageStatus`, `contextUsed`, `contextSize`, and `reportedCostDecimal`; new usage rows store `{}` in the legacy raw field. `reportedCostDecimal` is the exact per-turn OpenCode USD delta, as decimal text.

Claude computes SHA-256 over the current non-empty instruction text at every turn. `claudeInstructionSha256` records the hash last proven applied by a successful turn; failed turns do not advance it. A changed hash causes Claude to resume with the new private instruction file and `--system-prompt-snapshot off`; an unchanged hash leaves Claude's default snapshot behavior intact. The daemon stores the hash in the turn snapshot, never the instruction text. Claude writes instruction files under its private temporary directory and pairs each `instruction-*.txt` with an `instruction-*.lock` containing the owner PID. On Windows it removes inherited ACLs and grants full control to the current domain user via the system `icacls.exe`; on Unix it uses directory mode `0700` and file mode `0600`. If Windows ACL setup fails, instruction text is not written and turn admission is rejected. Provider exit and spawn failure remove the pair; startup cleanup removes only old paired Bitbots files whose owner PID is no longer live.

Every prompt reloads the persisted agent options and validates non-null model, thinking, and service tier values against the runtime's current cached or fetched authoritative catalog. An authoritative catalog rejects unknown IDs or unsupported combinations as a turn-scoped `invalid_argument`; when discovery is unavailable or the catalog is marked `fallback`, non-empty custom IDs are accepted without validation. Gate or adapter preflight rejection records the user message, error turn, rejected snapshot, and `exec.options.rejected` event atomically and does not reserve concurrency or deliver the prompt.

Codex `serviceTier` is sent on thread start/resume only when it is a catalog tier ID. The special value `standard` means standard speed for one Codex turn and is sent as `serviceTierForTurn: "default"`; it is never sent as a `serviceTier` ID. The legacy value `fast` is invalid; use the catalog ID (for example, `priority`) returned by the runtime.

`runtime.capabilities.settings` has `model`, `thinking`, `serviceTier`, `instructions`, and `customEnv` entries, each `{supported,enabled,scope,evidence,reason?}`. The `customEnv` entry also returns an `allowedKeys` array containing `LANG`, `LC_ALL`, `TZ`, `NO_COLOR`, and `TERM`. `enabled` is `supported && exec_gate.<provider>.<setting>`; custom environment support uses the provider allowlist and has no execution gate. `globalConcurrency` is `{limit,active}` with a fixed limit of 4. With `agentId`, `agentConcurrency` is `{configuredMaxConcurrency,effectiveMaxConcurrency,active}`; effective is the lower of the configured cap and 4. Without `agentId`, `agentConcurrency` is null and `agentConcurrencies` lists the active agents for that runtime. All active counts in this foundation reflect current daemon turns; durable reservation enforcement is a later step.

Persisted events include `settings.changed` `{key,enabled}` for actual `exec_gate.*` changes; no-op gate writes produce no event. `exec.options.changed` is `{sessionId,turnId,agentId,runtimeId,requested,applied,snapshotId}`. `requested` contains typed values, `instructionsPresent`, concurrency and environment key names only. `exec.options.rejected` is `{sessionId,agentId,runtimeId,setting,code,reason,turnId?,snapshotId?}`; session-scoped errors omit the optional fields, turn-scoped preflight errors include them. Codex app-server JSON-RPC rejection of thread start/resume settings emits one session-scoped event for each requested option before returning `provider_error`; rejection of turn settings emits turn-scoped `ExecApplied` evidence and does not retry. Payloads never contain instruction text, environment values, arguments, file paths, or raw provider JSON. A closed gate or unsupported non-null option returns `unsupported` with the safe execution-check message; failed provider discovery returns `provider_unavailable`, malformed provider catalog returns `provider_error`.

`usageSummary` fields are `{from,to,inputTokens,outputTokens,cacheReadTokens,cacheWriteTokens,reasoningTokens,providerReportedCostMinor,providerReportedCurrency,apiEstimateMinor,apiEstimateCurrency,pricingStatus,subscriptionFixedMinor,subscriptionCurrency,quotaState}`; analytics cost objects also include `mayBeHigh` when a conservative pricing tier was selected because turn usage omitted its discriminator. Pricing rules use decimal strings per million in `{id,provider,canonicalModelId,aliases,inputPerMillion,outputPerMillion,cacheReadPerMillion,cacheWritePerMillion,currency,effectiveFrom,effectiveTo,sourceUrl,checkedAt,notes,tiers,source}`. Tiers encode long-context thresholds, UTC time windows and cache-write durations. Subscription plans are `{id,provider,billingMode:"subscription",currency,monthlyMinor,renewalDay,quotaState}`.

The versioned official price table is `crates/bloblex-usage/data/official-prices.json`. Estimates resolve user override, official price list, cached OpenCode catalog estimate, then unknown. Unknown rates remain unpriced/null; explicit zero rates are known Free prices. Currency minor-unit conversion rounds half up after summing the exact decimal bucket values.

Existing clients retain hydrated message and activity arrays when applying it. `session.deleted` permanently removes that conversation and its persisted session-specific events. Unsupported semantics remain unsupported; never synthesize provider success, auth, usage or permission grants.

Usage token buckets are mutually exclusive: `inputTokens` excludes `cacheReadTokens` and `cacheWriteTokens`; output, reasoning and provider-reported cost are separately nullable. Valuation basis is `provider_reported_actual`, `api_rate_estimate`, `subscription_fixed`, `local_free`, or `unknown`. Unknown model price serializes as `null` with an explanatory status, never zero.

Otherwise the reported input count is retained with an evidence note. Codex usage has no reported cost and its model comes from the thread start/resume echo. Failed Codex turns report `usageStatus: "unreported"` with nullable token and model fields.

Provider prompt delivery is recorded internally on the turn (`turns.data.delivery`): `acknowledged` when the provider accepted the prompt, `unknown` when a turn ended without that evidence. It is never emitted as a wire event and adds no client-facing field.

## Errors and compatibility

Stable error codes: `invalid_argument`, `not_found`, `unauthorized`, `unsupported`, `provider_unavailable`, `provider_error`, `budget_blocked` (retired; no emitter found), `conflict`, `replay_gap`, and `internal`. Error messages are safe for display and contain no credential material or prompt text. A client must compare `v`; an unsupported major version is a startup error. Adapter capability omissions mean unsupported.

The execution snapshot RPCs use `invalid_argument` for malformed IDs, cursors, or limits; `not_found` for a missing snapshot, session, or runtime. `runtime.capabilities` returns `not_found` for a missing runtime and `invalid_argument` when the supplied agent belongs to another runtime. Later option application uses `unsupported` for closed gates or unsupported settings and `provider_unavailable` when the provider cannot be reached.

## Security invariants

- Loopback-only listener and random per-process capability; no LAN exposure.
- Remote mode (design): the second listener also binds loopback only, is reachable from other machines only through `tailscale serve` on the owner's tailnet, never through Funnel, and never sees the capability.
- Capability is memory-only and passed to the desktop shell only through daemon stdout at startup.
- Renderer never receives the capability or connects directly to the daemon.
- Process launch is direct executable plus argument array. User input never becomes shell text.
- Logs redact secrets and exclude prompt bodies by default.
- SQLite and runtime records never receive provider login credentials.
- Claude hook bridge has a bounded request and timeout and fails open when daemon IPC is unavailable.
- Permission replies use a pending→resolved conditional update; duplicate replies return `conflict` and never reach the provider twice.
- Retired (AGENTS.md, 12 October 2026 amendment; `crates/bloblex-daemon/src/main.rs:2413` notes historical budget records are not enforced). The former rule: budget admission reads applicable usage and reservations, then inserts a reservation in one `BEGIN IMMEDIATE` transaction. The strictest applicable hard policy governs; simultaneous prompts cannot share the same remaining allowance.

## Runtime hardening additions

- `runtime.capabilities` adds `versionRecognized: boolean`, the runtime's version-format recognition result.
- `turn.error.failureClass` may be `context`; its safe message is `Context window is full. Start a new conversation.` and `canRetireSession` is true. The provider-session ID remains intact on context exhaustion.
- Mixed-currency analytics keep each currency's valuation separately. The scalar cost is null when currencies are mixed; `excludedCurrencies` lists currencies after the first sorted currency because the scalar shape cannot represent them. `lowerBound` is true for mixed currency totals.
- `session.resume_rejected` reports positive evidence that a stored provider session is missing or expired. The daemon clears that provider ID and starts a fresh session; generic resume errors do not clear it.
- `session.replaced` reports that the provider's conversation context changed. Its payload is `{"sessionId","reason","contextLost"}`, where `reason` is `compaction` or `fresh_session` and `contextLost` is true only when earlier context is gone. It is informational; the persisted `message.completed` notice carries the user-facing copy and `session.context.reset` still clears the context meter for a lost context.
- The daemon's startup/no-progress watchdog is 45 seconds; after the first semantic activity, its semantic-inactivity watchdog is 300 seconds. These are Bitbots product choices, not provider CLI facts. Expiry fails the turn with `failureClass: timeout` and closes the adapter session, which kills its owned process tree.
- Resume-time context overflow emits `session.context_exhausted` with the safe message and retirement offer; it does not clear the provider-session ID.

## Wave 14: Bitbots MCP

The Bitbots MCP lets a Claude Code session the owner started outside Bitbots see and drive the running app. It is off by default and is never a remote (paired device) surface.

**Settings.** `mcp.external.enabled` (boolean, default false) and `mcp.external.tier` (`viewer`, `chat` or `operator`, default `chat`) are stored settings, but `settings.set` refuses every key under `mcp.external.` with `invalid_argument` ("use external.enable"). They move only through the `external.*` methods.

**Capability RPCs (the app's Settings page; never remote).**

- `external.status` returns `{enabled, tier, endpointPath, bridgePath, command, lastCallAt, lastClient}`. `command` is the `claude mcp add bitbots -- "<bridge>" mcp-server --endpoint "<endpoint file>"` line; `endpointPath`, `bridgePath` and `command` are null while the MCP is off, and `command` is null when the bridge copy does not exist. `lastClient` is the MCP client's `clientInfo.name`. The token is never in a result.
- `external.enable {tier?, confirm: true}` refuses without `confirm` (`invalid_argument`), makes a new token, writes the endpoint file `mcp-external.json` (`{address, token}`) in the data folder, copies the daemon executable to `bitbots-mcp.exe` beside it (a locked copy is kept), stores the settings and broadcasts. `tier` defaults to `chat`.
- `external.disable` clears the token in memory, deletes the endpoint file, stores `enabled: false` and broadcasts.
- `external.setTier {tier}` and `external.rotate` work only while enabled (`conflict` otherwise). Rotating writes a new token and file; running servers read the file again on a 401.
- Event `external.changed`: the status object. Calls broadcast it at most once every five seconds.

**Tool route (not in `dispatch`).** `ext.hello {clientName}`, `ext.tools.list` and `ext.tools.call {name, arguments}` need `Authorization: Bearer <MCP token>` and `mcp.external.enabled == true`; otherwise `401 unauthorized`. The token is compared in constant time and is not the daemon capability. `bitbotsd mcp-server --endpoint <file>` is the stdio server a client runs: it sends `ext.hello` after `initialize`, reads the endpoint file again when a call gets 401 or cannot connect, and allows a call to run 660 seconds (`wait_for_turn` waits at most 600). Every call updates `lastCallAt` and writes a content-free activity line (kind `mcp`: the client, the tool and the bot's name, never message text).

**Tools by level.** A tool above the current level is missing from `tools/list` and refused in `tools/call` (`isError`: "This tool needs the Operator level in Bitbots › Settings › Connections.").

- `viewer`: `get_status`, `list_bots`, `list_runtimes`, `list_projects`, `list_conversations`, `read_conversation`, `wait_for_turn`, `turn_metrics`, `worktree_status`, `list_approvals`. Results hold allowlisted fields only: never environment values, instructions, profiles, the capability or the token. Unknown metrics are left out, never 0, and no cost is reported.
- `chat`: `send_message` (a bot or a conversation; busy conversations queue the message; new conversations only in the bot's own folder or a registered project), `steer`, `stop_turn`.
- `operator`: `send_message` with `worktree: true` (a new conversation in its own linked git worktree, as delegations use; refused outside a git repository) and with any `projectPath`, `create_bot` (through the same catalog validation as `agent.create`; permission mode `ask` or `auto`, never `bypass`) and `answer_approval` (`allow` or `deny`).

**Origin mark.** A user message sent through `send_message`, a queued `send_message` or `steer` carries `meta.origin = {kind: "mcp", client}` (`client` is the last client name, or "MCP"). Snapshots and `session.get` carry it unchanged, so the app can show "via Claude Code"; the remote redaction passes it through (it holds no path).

## Phase 1, Lane B: sign-in read, experiments, shortcuts and shims (30 October 2026)

**The usage-bar sign-in read is opt-in.** `usage.readCliSignIns` (JSON boolean, off unless it is an explicit `true`; validated by `settings.set` and `validate_setting_value`) is the owner's consent for the daemon to read Claude Code's `.credentials.json` and OpenCode's `auth.json` or credential database, read-only, to fetch a usage bar. While it is off, no path opens those files or that database: the gate is the first statement of `poll_local_quota`, so `poll_provider_quotas`, `quota.refresh`, the retry policy's `refresh_provider_quota` and the switch itself are all covered. A provider then reports `read_off` in `quota.list`'s `lastError`, in the place `no_credentials` is reported, and keeps no snapshot (`snapshot` and `fetchedAt` are null), so no stale bar shows; the retry policy then sees an unknown reset and declines a rate-limited retry with `unknown_reset` instead of probing for one. Turning the switch on polls soon after (`poll_local_provider_quotas` is spawned; no restart), turning it off clears both snapshots at once with a `quota.updated` per provider. Codex is unchanged: its usage comes from its own app server, not a credential read. The key never travels in a backup (`exportable_setting`) and is not in the remote settings allowlist.

**The useful experiments are on by default.** `experiments::on(&settings, name)` is the one read: `experimental.memory`, `experimental.autoTitles`, `experimental.autoRetry` and `experimental.undo` are on when the key is absent and off only when it is an explicit `false`. A stored `false` stays off. `experimental.search`, `experimental.changeReview` and `experimental.messageActions` are read only by the UI and are not part of this rule.

**Shortcuts (validated settings only; the UI owns the behaviour).** `composer.sendShortcut` is `enter` (the default when absent), `ctrl+enter` or `shift+enter`. `shortcuts.bindings` is an object of at most 40 entries, each action id 1 to 60 characters of `[a-zA-Z0-9.-]` and each value a string of up to 40 printable ASCII characters (`0x20` to `0x7e`) or `null` for "no shortcut"; anything else is `invalid_argument`. Both broadcast `settings.changed` and are in the backup allowlist, like the other appearance settings.

**Renamed setting keys move once.** `SETTING_SHIMS` in `crates/bloblex-storage/src/lib.rs` is a table of old key, new key and an optional value mapping. At every `Storage::open` (and `open_in_memory`), in one transaction, an old key's mapped value is written under the new key only when the new key has none (an existing value wins), and the old key is deleted; with nothing to move it does nothing. `Storage::backup_import` runs the same table inside its transaction, so a restored old key lands under its new name. Searched on 30 October 2026 (`git log -S`, and a scan of every revision of `crates/bloblex-daemon/src/main.rs`, `crates/bloblex-storage/src/lib.rs` and the UI's `settings.set` calls): no setting key has ever been renamed, so the table is empty and only test-only entries (`test.oldKey`, `test.oldCount`) exercise it.

## Phase 4: machines (31 October 2026)

A machine link is this daemon acting as a paired device of another machine's Remote gateway. The window never talks to the other machine; there is no new listener and no relay. A conversation on another machine is read-only here. Every method below is `tiers.json` class `never` (family `machine.*`) except `machine.info`, class `read` at `viewer`, which is what the other side asks for. Events `machine.changed` and `machine.pair.changed` are `drop`. None of these go on the Bitbots MCP.

**Identity.** Settings `machine.id` (a UUID made at first start) and `machine.name` (default: the host name, 1 to 60 characters). Neither travels in a backup, and `settings.set` refuses both (`invalid_argument`); the name changes only through `machine.self.rename`.
- `machine.self {}` and `machine.self.rename {name}` give `{id, name, version}`.
- `machine.info {}` gives `{machineId, name, version, handoffVersion: 1}`.

**Links.** Table `machine_links(id, name, url, auth, fingerprint, tier, paired_at, last_seen_at, state, device_id)`, where `id` is the other machine's `machine.id`. The device token is never in the database: it lives in `<data>/machines/<id>.token` (user-only) and is never returned, logged, exported or put in a diagnostics bundle.
- `machine.probe {url}` gives `{origin, reachable, isBitbots, auth: "code"|"password", fingerprint, trusted}`. It calls `GET /api/ping` and sends no credential and no `Origin`. `trusted` means web PKI accepted the certificate (`auth: "code"`, `fingerprint: null`). Otherwise `auth: "password"` and the owner compares `fingerprint` with the other machine's screen.
- `machine.pair.begin {url, code, username, password, fingerprint, confirm}` gives `{job}` at once. A non-empty `fingerprint` selects the password sign-in (`username`, `password` and the accepted `fingerprint` are required); otherwise `code` is required. No `confirm: true` is `invalid_argument`. Job: `{id, url, state: "pending"|"approved"|"rejected"|"expired"|"failed"|"cancelled", detail, machine}`; event `machine.pair.changed {job}`. The job never holds the password.
- `machine.pair.cancel {id}` gives `{job}`; `machine.pair.list {}` gives `{jobs}` (memory only).
- `machine.list {}` gives `{machines: [{id, name, url, auth, fingerprint, tier, pairedAt, lastSeenAt, state: "online"|"offline"|"revoked", detail, version, bots}]}`.
- `machine.rename {id, name}` is a local label only. `machine.remove {id, confirm}` signs the device out best effort, deletes the token and the row, and gives `{removed, signedOut}`; it succeeds when the other machine is away.

**Reading the other machine.** While a link exists, every 20 seconds each link is asked for `machine.info`, `agent.list` and `session.list` (10 second limit; one machine never holds up another). The result is kept in memory only. `bots` is `[{id, name, color, outfit, look, role, provider, model, busy, activeSessionId, conversations}]`, without hidden bots; an offline machine keeps its last list. Each read also asks the other machine for this device's own tier (`GET /api/me`) and stores it when it changed; a failed read keeps the stored tier. `machine.changed {machineId, state}` carries nothing else, because events are stored and the other machine's bots are not: the window reloads `machine.list`. The `machine` in a `machine.pair.changed` job always has an empty `bots`.
- `machine.refresh {id}` gives the row now. `machine.conversations {machineId, agentId}` gives the other machine's `agent.conversations` unchanged. `machine.conversation {machineId, sessionId}` gives `{session}` wrapping its `session.get`. All of them pass through the gateway's redaction.
- When the other machine can't be reached these answer `provider_unavailable` with "`<name>` can't be reached right now."

### Phase 4: handoff (31 October 2026, Round 2)

A conversation moves by being **pulled**: the machine that wants it asks the machine that has it. `session.data.link.movedTo` is `{machineId, name, at}` and means another machine runs this conversation; a bot's own conversation may have no other `link` key at all (no `kind` is a main conversation). With `movedTo` set, `session.prompt`, `session.steer`, `session.warm`, `session.resume`, `session.queue.add` and every other start of a provider process answer `conflict` "This conversation moved to `<name>`. Take it over to continue."; during a live lease the same calls answer "This conversation is moving to `<name>`."

**On the machine giving it up** (`tiers.json` class `handoff`, family row `handoff.*`: tier `operator`, refused in quiet hours, and `rpc_post` refuses a device whose `kind` is not `machine` with `forbidden_remote`; the result is not field-redacted, so it holds no host path):
- `handoff.preview {sessionId}` gives `{ready, reason, title, bot: {id, name, provider, model}, repo: {identity, url, branch, isWorktree, hasRemote}, uncommitted, commitsAhead, movedTo}`. `reason` is the first of: already moved, working, waiting on an approval or question, queued messages, assignments running, Manager's conversation, or not a bot's own conversation (a side conversation, automation, board task, group, or the child of an assignment). `movedTo` is `{machineId, name}` or `null` and lets the other machine finish a move it already committed.
- `handoff.prepare {sessionId, commitUncommitted, toMachineId, toName, confirm}` gives `{handoffId, steps: [{id: "commit"|"push", status: "done"|"skipped"|"failed", detail}], package}`. It takes a lease (one per conversation, 10 minutes, memory only), commits only in the conversation's own copy and only with `commitUncommitted`, and pushes `bitbots/<branch>` with `git push -u origin`, never forced and never the base. A failed step ends the lease and answers `handoffId: null, package: null`. `package` is `{version: 1, session: {id, title, createdAt, branch, isWorktree}, bot (the backup's export), repo: {identity, url, branch, head}, note, messages: [{id, role, content, createdAt}], truncated, omitted: {pictures, toolSteps}}`: roles `user`, `assistant`, `notice` only, the newest 2,000 and at most 16 MiB, no thinking, tool output, attachment or host path.
- `handoff.commit {handoffId}` sets `link.movedTo`, writes the notice "Moved to `<toName>`.", closes the provider process and ends the lease; an unknown or expired lease is `conflict`. It takes the session gate that a new send takes, so a send and a move cannot both win. `handoff.abort {handoffId}` ends the lease (commits and pushes stay).

**On the machine taking it** (`never` remote; events `drop`):
- `machine.takeOver.preview {machineId, sessionId}` gives the giving machine's preview with the local match merged in: `{ready, reason, title, bot: {id, name, provider, model, agentId, willCreate}, repo, uncommitted, commitsAhead, project: {id, name}|null, needsProject, runtimeReady}`.
- `machine.takeOver {machineId, sessionId, projectId, commitUncommitted, confirm}` gives `{job}` at once. Job `{id, machineId, state: "running"|"done"|"failed", steps: [{id, status, detail}], sessionId, detail}`; `steps` grows as each finishes, with ids `prepare`, `code`, `bot`, `import`, `commit`, `open`. Event `machine.takeOver.changed {job}`; `machine.takeOver.list {}` gives `{jobs}` (memory only, newest 20).
- Nothing can run on this machine until `open` clears `movedTo`, and the giving machine stops being able to run it at `commit`. Before `commit` a failure calls `handoff.abort`, removes what the import made (or puts a returning row back as it was) and leaves the giving machine with the conversation. A created bot never has Full access (its mode becomes this machine's default) and never has environment values.

## Phase 5, section 4: the Codex protocol pin

`crates/bloblex-adapter-codex/schema/` is the Codex app-server protocol as one installed `codex-cli` generated it (`scripts/codex-schema.ps1`, `--experimental`, `codex-cli 0.165.0`): `ClientRequest.json`, `ClientNotification.json`, `ServerRequest.json`, `ServerNotification.json`, `compat/` for two notification types older builds still emit, and `VERSION`. A test checks that every method the adapter sends and handles (`crates/bloblex-adapter-codex/src/protocol.rs`, `METHODS`) is in the pin, so a Codex update that removes one fails a test rather than a turn.

Rows for other providers have `protocol: null`. A mismatch is not a refusal: the agent runs, and `doctor.run` adds one `warn` row, `runtime.<id>.protocolSchema`, with the sentence "Codex x is newer than the version Bitbots was checked against (y)." (or "is not the version ..." when the installed CLI is older). The row carries no fix, because nothing needs fixing.

## Phase 5, section 3: Gemini CLI and Qwen Code over ACP

`crates/bloblex-runtime/src/providers.rs` holds one table of the ACP providers Bitbots discovers and runs: `{provider, displayName, command, args, signInCommand, installHint}`. Today that is `gemini` (Gemini CLI, `gemini --acp`) and `qwen` (Qwen Code, `qwen --acp`); both CLIs still accept `--experimental-acp` but deprecate it in favour of `--acp`. OpenCode is not a row: it keeps its own discovery, credential read and the `acp` subcommand, and its behaviour is unchanged. `bloblex_runtime::is_acp_provider` is the one answer for "does this provider speak ACP" (OpenCode plus the rows), and `acp_launch_args` is the one answer for how to launch it (`acp` for OpenCode, `--acp` for a row).

A provider in the table is discovered like the others — not installed means not listed, an installed CLI whose `--help` does not mention ACP is kept as an error row and retried — and then runs through the existing ACP adapter: sessions, turns, tools, approvals and the models `session/new` reports, with no adapter code of its own. `runtime.list` rows carry `protocolFamily: "acp"`; `runtime.capabilities` gives the same honest row OpenCode gets by the same adapter code (`model`, `thinking` and `instructions` from the session, no `serviceTier`, no `steer`), and `thinking` stays behind its execution gate until a real CLI is verified. `agent.create` and bot proposals accept both new providers; attachments and images are accepted for them as for OpenCode; a sign-in failure names the table's own command (`run gemini in a terminal and sign in there`).

No new RPC, no tier change, nothing on the Bitbots MCP. Capability rows for an unknown provider stay `false`: nothing is claimed about a coding agent Bitbots cannot run.

## Phase 5: secrets and one-use secret requests (31 October 2026)

All of these are `tiers.json` class `never` and the event `secret.request.changed` is `drop`: nothing here crosses to a device, and the secure form exists only at the desktop. The code is `crates/bloblex-daemon/src/secrets.rs`, with `agent_env_refs` in `crates/bloblex-storage/src/secret_refs.rs`.

### Secrets in the credential store

A secret is a named value in Windows Credential Manager, target `Bitbots/<name>`, generic, persisted for the local machine. `name` is 1 to 64 of `[A-Za-z0-9_.-]`, the value 1 to 2,048 bytes of text. **No RPC returns a value.** The value is never in the database, an event, a log, a reply, a backup or a diagnostics bundle.

- `secret.list {}` gives `{secrets: [{name, updatedAt, usedBy}]}`, where `usedBy` is the names of the bots that point at it.
- `secret.set {name, value, confirm}` gives `{name}`. No `confirm: true` is `invalid_argument`; an existing name is replaced.
- `secret.delete {name, confirm}` gives `{deleted: true}`. A secret a bot still uses is `conflict`, naming the bots.
- `agent.create` and `agent.update` accept `envRefs: {ENV_KEY: secretName}` (`null` or `{}` clears it; omitting it keeps it), and `agent.get`, `agent.list` and the create and update replies carry it. A key is a plain variable name (letters, digits, underscore, at most 128) and may look secret (`API_KEY`); `PATH`, `SYSTEMROOT`, `COMSPEC` and the other process-shaping names, and anything starting `BITBOTS_` or `BLOBLEX_`, are `invalid_argument`. The secret need not exist when it is saved.
- At spawn (a new session, a resumed session and every prompt) the values are read and join the environment beside `customEnv`. A missing secret fails the call with `conflict` and a sentence naming the secret, never a value.
- A backup carries `envRefKeys` (the variable names) and nothing else; a restored bot has no references. A handoff carries none. Devices never see `envRefs` (field rule in `policy.rs` and `remoteTiers.ts`, goldens `phase5-*`).
- A coding agent can read its own environment, so this protects a value at rest, not from the bot.

### One-use secret requests

The bot tool `request_secret {name, reason}` (`reason` at most 300 characters) joins the tools beside `ask_user`, offered wherever `ask_user` is. In a conversation nobody watches (an automation, an unattended task, or a delegated child whose origin chain holds one) it is not offered and a call answers a plain sentence without asking. Auto-approve and Full access never answer it.

The call **waits** for the owner for up to 50 seconds (the team bridge's limit is 60). The request is held in memory only, so a restart ends it. It ends on an answer, a decline, the end of the turn (a cancel included) or the time limit, and a late answer is `conflict`. One request per conversation is open at a time.

- `secret.request.list {}` gives `{requests: [{id, sessionId, name, reason, botName, expiresAt}]}`.
- `secret.request.answer {id, value}` (1 to 16,384 bytes) gives `{answered: true}`; `secret.request.decline {id}` gives `{declined: true}`. A request that is no longer waiting is `conflict`.
- Event `secret.request.changed {id, sessionId, name, reason, botName, expiresAt, status}` with `status` `pending`, `answered`, `declined`, `cancelled` or `expired`. It never carries a value.
- On an answer the value goes to `<data>/one-use/<id>`, created empty, restricted to the current user, and only then written. The tool result names that path and nothing else. The file is deleted when the turn ends, and the folder is emptied at startup. The conversation gets the notice "You gave Rae NAME for this turn."
- The bot can read the file, and what it does with the value is up to it.


## Phase 5: accounts (31 October 2026)

**Who is signed in.** Every `runtime.list` row gains `account: {label, plan, source} | null`: who the provider's CLI says is signed in, read only from that CLI's own output during runtime discovery, with a 10-second limit that kills the process. `label` is an email or account name (`null` when the CLI does not say), `plan` is the plan name (`null` when it does not say), and `source` is fixed text naming the command: `claude auth status`, `codex app-server account/read`, or `opencode auth list`. A failed, timed-out or unrecognised answer is `account: null`, and a row saved before this field reads as `null`. No token or credential file is opened for it: the usage-bar exception in `AGENTS.md` does not cover this field.

- **Claude Code:** `claude auth status` prints one JSON object; `label` is `email` and `plan` is `subscriptionType` (real example: `pro`), taken only when `loggedIn` is `true`.
- **Codex:** the app server's `account/read` (initialize, then `account/read`, skipping the `account/updated` notification it sends first). A ChatGPT account gives `email` and `planType` (real example: `plus`); an API-key or hosted account answers with both fields `null`.
- **OpenCode:** `opencode auth list` lists integrations (`OpenCode Go  API key  stored`) and names no person, so both fields are `null`. A person is only reported when a row carries an explicit `email`/`account`/`username` field, or an email-shaped value; a `label` field is the credential kind and is never used.

`account` is sent to paired devices at `viewer` (the owner sees it on a phone too) and is pinned by the `runtime-list-account` golden in `apps/desktop/src/remote/fixtures/policy-goldens.json`.

### Several accounts per provider (31 October 2026)

An account is a named config folder for one provider. The default account is the CLI's own folder: it has no row, cannot be deleted, and is what a bot uses when its `accountId` is `null`. Table `accounts(id, provider, name, created_at)` in `crates/bloblex-storage/src/phase5.rs`; the folder is `<data>/accounts/<id>`, created user-only, and every path is built by `accounts::account_folder`, so a delete can only ever remove a folder inside `<data>/accounts`. The environment table is one function: Claude `CLAUDE_CONFIG_DIR`, Codex `CODEX_HOME`, OpenCode `XDG_CONFIG_HOME` and `XDG_DATA_HOME`, all pointing at the account's own folder. Nothing here reads a token or a credential file.

- **`account.list {}`** gives `{accounts: [{id, provider, name, signedIn, label, plan, bots}]}`. It **never runs a CLI**: `label`, `plan` and `signedIn` come from memory, last written by `account.check` (or the check after `account.create`), and an account not yet checked is `signedIn: false` with both fields `null`. `bots` is how many bots point at it.
- **`account.create {provider, name}`** gives `{account}`. `provider` must be `claude`, `codex` or `opencode`; `name` is 1 to 60 characters. It creates the folder, sets it user-only, and runs one check so the first `list` has an answer.
- **`account.rename {id, name}`** renames the row only; the folder keeps its id.
- **`account.delete {id, confirm}`**: no `confirm: true` is `invalid_argument`; a turn running on one of its bots is `conflict` and keeps the folder; otherwise the bots go back to the default account and the folder is removed.
- **`account.signIn {id}`** gives `{command}`: one PowerShell line with the environment set for that command only, for example `$env:CLAUDE_CONFIG_DIR='<folder>'; claude auth login`. The folder is quoted with single quotes and an inner quote is doubled. It holds no secret.
- **`account.check {id}`** asks the CLI again and remembers the answer, so a later `list` is instant.
- All six are `tiers.json` class `never`: an account is a host-side folder, and the sign-in command is for the owner to run. Usage bars keep reading the default account only; the quota reader never consults `accounts`.

**Bots.** `agent.accountId` is a string or `null`, through `agent.create` and `agent.update` and readable in `agent.list`. An id that does not exist, or that belongs to another provider than the bot's runtime, is `invalid_argument`. It never travels in a backup (`backup::export_bot` is an allowlist that does not name it) or in a handoff, which carries that same bot export: a restored or moved bot gets `null` and lands on the default account. At spawn the account's variables join `options.env` beside `customEnv`; `options.env` is part of the shared-process key in the Codex and ACP adapters, so two bots on different accounts get separate provider processes, and Claude spawns per conversation anyway.

### Custom models (31 October 2026)

A custom model is a name the owner typed for a model a provider's catalog does not list. Table `custom_models(id, provider, model_id, label, efforts_json, created_at)` in `crates/bloblex-storage/src/phase5.rs`, unique on `(provider, model_id)`. It holds no secret, never enters a catalog cache, and a restored one is just a name.

- **`model.custom.list {provider}`** gives `{models}`; `provider` must be `claude`, `codex` or `opencode`.
- **`model.custom.save {id, provider, modelId, label, efforts}`** gives `{model}`. Without `id` it creates; with a known `id` it updates. `modelId` is 1 to 200 characters with no whitespace, `label` at most 80, `efforts` at most 8 strings of at most 24 characters. A second name for the same provider and model id is `conflict`, and so is an id the provider's **cached** catalog already lists — a save never polls a provider.
- **`model.custom.delete {id}`** gives `{deleted: true}`, or `not_found`.
- `runtime.models` merges them **after** the catalog's own entries, each with `source: "custom"`; the rest of that reply is unchanged.
- A bot picks one as its `model` and the turn passes it to the CLI unchanged; a name the CLI refuses fails that turn in the normal way.
- All three are `tiers.json` class `never`. A backup carries them in `contents.customModels`, and an import puts back any the host does not already have: nothing about them is sensitive.

### Webhook triggers (31 October 2026, Phase 5 section 8)

An automation can be started by a signed HTTP request instead of, or as well as, its schedule. The design and its limits are `docs/remote/THREAT_MODEL.md` §18; this is the wire shape.

- **`automation.webhook.enable {id, includeBody, confirm}`** gives `{url, secret, webhook}`. `confirm: true` is required. A new 256-bit secret is made every time, so an old one stops working. `secret` appears in this reply **only**: it is not in the DTO, an event, a backup or a diagnostics bundle. `url` is `null` while Remote is off, and otherwise `"<gateway address>/api/hook/<id>"`.
- **`automation.webhook.rotate {id, confirm}`** gives `{url, secret, webhook}` with a new secret; `conflict` when the webhook is not on.
- **`automation.webhook.update {id, includeBody}`** gives `{webhook}`, so changing whether the body reaches the prompt does not mint a secret. On a webhook that is off it leaves `includeBody` false.
- **`automation.webhook.disable {id}`** gives `{webhook}` and deletes the stored secret.
- `secret` is lost for good once the reply is gone; the only recovery is `rotate`, which invalidates the old one.
- Every automation DTO carries `webhook: {enabled, includeBody, url}` — the address, never the secret. `url` follows Remote: `null` while it is off.
- All four are `tiers.json` class `never`: only the desktop turns a webhook on, rotates it or changes what it may include.
- **The route:** `POST /api/hook/<id>` on the gateway, outside the `Origin` and Native `Host` checks (a sender is a machine with no cookie) and inside the per-source abuse bucket. Body at most 64 KiB; a larger one is answered like any other failure. `X-Bitbots-Timestamp` is Unix seconds and must be within 300 s; `X-Bitbots-Signature` is `sha256=<hex HMAC-SHA-256 of "<timestamp>.<body>">`, compared in constant time. An accepted signature is remembered for 600 s, so a replay is a failure. Every failure is exactly the `404` an unknown id gets, and one HMAC is computed on every request, so an id cannot be discovered by timing. Failures count toward that source's own lockout (5 in 60 s → 60 s); a valid signature is never refused by it.
- **Accepted** answers `202 {"accepted": true}` whether the automation ran or was paused, disabled or already running, so a valid signature cannot tell them apart; the difference appears only in the owner's activity list, as one content-free line.
- **The body** is off by default. When `includeBody` is on it reaches the prompt only inside a `<bloblex_webhook>` block as inert quoted data (`&`, `<`, `>` escaped, as `knowledge.rs` `inert` does), after one sentence saying it is data. It is never stored, logged, evented or echoed.
- **Fences:** the run goes through the automation path, so it takes the automation's `plan`/`auto` mode (never `bypass`), `maxRuntimeSecs`, single flight, the global pause and the concurrency limit.
- **Deleting an automation deletes its secret.** A backup carries no webhook field and no secret, and an import creates the automation with the webhook off: it never comes back on by itself.
